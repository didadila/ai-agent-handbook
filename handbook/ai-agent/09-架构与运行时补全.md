## agent.arch.workflow：什么时候需要动态决策

**结论**：下一步能预先写清时先用 workflow；下一步依赖运行时未知事实、需要模型判断时再引入 Agent。

**案例**：每天从三张固定表计算销售报表，用模型决定取哪张表，导致偶尔漏掉退款数据。流程本来固定，动态选择引入了不必要的不确定性。相反，排查未知报错时，是否查日志、读配置或运行复现取决于上一轮证据。

**机制**：workflow 将路径和转移条件编进程序，模型可作为其中一个受约束步骤；Agent 把部分路径选择留给运行时推断。两者可组合，边界由决策是否可预定义决定。引入动态决策后要额外承担轨迹验证、预算、停止和恢复成本。[Anthropic 架构说明](https://www.anthropic.com/engineering/building-effective-agents)

**误解靶子**：业务步骤多，所以必须用多 Agent。步骤多只说明流程长，不说明路径未知。

**判据**：在看到本轮工具结果前，能否写出完备、可维护的下一步转移规则？能写出时优先确定性流程。

**自测**：为“审批规则固定、输入是自由文本”的报销流程划出唯一需要模型判断的边界。

## agent.runtime.durable：恢复的是任务，不是聊天

**结论**：长期任务需要持久化执行状态；恢复时仍要处理副作用已提交而 checkpoint 未写入的窗口。

**案例（构造）**：退款成功后进程退出，尚未来得及保存“步骤完成”。重启后按旧 checkpoint 再退款。模型完整记得计划也无法单凭聊天判断服务端是否已退款，必须查询权威结果或对账。

**机制**：保存任务、步骤输入、外部操作标识和状态；每次尝试使用同一业务幂等键。任务租约控制执行权，外部写入还需去重或 fencing 防止旧执行者继续提交。恢复时先核对未知步骤结果，再推进。暂停审批是持久状态；部署升级需定义状态/schema 迁移，不能直接用新代码重放旧输入。运行时的重放能力不自动让任意外部接口获得 exactly-once。[Durable Task 官方资料](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-task-for-ai-agents)

### 三种状态：外部执行真值、记忆派生、模型上下文

| 对象 | 谁维护、说明什么 | 恢复边界 |
|---|---|---|
| **权威执行状态与外部效果** | 任务数据库保存租户、请求、租约、尝试与阶段；目标服务的操作 ID/结果查询或对账证明远端效果 | 本地 `succeeded` 只证明其提交契约覆盖的结果，不能自动证明任意远端副作用；本地与远端未原子提交时仍须核对 |
| **memory 及其派生表示** | transcript 记录当时说/做什么，notes、wiki、索引与摘要组织可复用信息 | 不是事务日志或当前授权真值；可错、过期、被撤销，删除须传播到派生副本和重建路径 |
| **本次模型上下文** | 宿主按任务、权限、版本与预算注入必要投影 | 清空或压缩不撤销业务效果；模型说 `done` 不能替代外部检查，未注入也不代表从未执行 |

structured artifact 能携带 spec/验收版本、checkpoint 引用、条件、证据、`unknown`、动作幂等键和授权范围，帮助换会话/换执行者；但**不能替代事务、租约/条件写、外部去重、对账或执行前授权**。字段被填上不证明内容真实，执行者也无权通过改验收期望来自评成功。

### checkpoint 与“外部成功、内部未记完成”的窗口

1. **先保存已接受的动作**：绑定任务/对象、规范化参数、版本、审批引用与稳定幂等键，记录待执行状态。重新执行不能换键，恢复也不能从模型摘要重造效果 ID。
2. **执行前再检查**：当前授权、对象/工具版本、剩余预算与执行权。旧 checkpoint 或旧工件中的许可不是永久授权；越界/撤权就暂停或拒绝。
3. **调用外部接口并确认效果**：成功返回后保存结果及外部操作 ID。checkpoint 与本地状态迁移尽量用同库事务，但普通外部 API 不会自动加入这笔事务。
4. **窗口内退出按 `unknown` 恢复**：请求可能已到达或已成功，不能把“checkpoint 未完成”解释为“没执行”。先按原操作 ID/幂等键 query 或对账，确认成功则补记而不重复；只有可靠地确认未执行且当前授权有效，才按同一业务键重试。目标系统不支持可靠查询/幂等时，保留未知并转人工，不能承诺 exactly-once。

process restart 先恢复耐久状态、重获有效租约并处理版本迁移；reset / clear-context 只是重建模型输入，compaction 只是有损替换历史。三者都不能丢已执行动作、未知结果、授权边界与版本，区别和跨会话验收协议见 [第 5 章](05-agent循环.md)；记忆四层、Dreaming 与删除规则见 [第 2 章](02-上下文工程.md)。

### 构造故障验收：沿用 Python 任务服务（未运行）

沿用本仓库 [job_service.py](../python-backend/examples/job_service.py) 的 `JobStore.submit/get/finish`、租户作用域、稳定请求幂等键和条件完成语义。现有示例是本地 SQLite + CLI 与确定性 stub，**没有完整 model-context reset、跨会话 harness、外部发布或记忆删除系统**。下表是这些扩展的设计验收案例，不是 demo 已有能力，也不是实测报告；`unknown` 是扩展的效果状态，不是现有 `tasks.status` 枚举。

| 构造故障 | 应检查的外部/持久证据 | 设计验收断言 |
|---|---|---|
| **clear-context 后已成功效果不重复**：任务已条件提交 `succeeded` 与结果，再清空模型输入 | 同租户 `get` 返回原 task ID、状态/结果；同键同请求 `submit` 复用原任务；监测扩展适配器效果次数 | 重建使用既有结果，不换键新建任务或重复成功效果；任务/受理事件不增加，扩展副作用次数不增加 |
| **unknown 先 query**：构造报告发布扩展，请求已发出但确认与 checkpoint 写入前退出 | 先查任务状态，再按原效果 ID/键查询发布适配器的权威结果；本地仍 `running` 不证明未发布 | 确认已发布则补记、重试次数为零；查询无定论则保留未知/转人工，不先发布第二份；`get` 本身不能证明远端效果 |
| **executor 只说 done，外部状态不通过**：执行者写了完成声明但任务仍未成功或结果不满足固定契约 | evaluator 独立读取同租户状态、结果、固定 spec/验收版本与检查证据 | 不标记验收通过，交接记录原因与下一步；即便 executor 改期望或自评 `pass` 也无效 |
| **删记忆不复活**：删除 note 后尝试恢复旧摘要、重建 wiki/索引/cache 或再次注入 | 受控删除/撤销版本覆盖 notes、representations、index、cache、摘要、原始记录留存和恢复路径 | 被删内容不再注入，旧工件/备份整编不能复活；当前撤权仍被拒绝。删除记忆也不撤销既有业务效果，必要耐久记录按授权/保留政策另行处理 |

这些案例只供进一步设计与验收，不扩充 [Python 五天路线](../python-backend/sprint-5-days.md) 的必学范围。Python 实现边界继续读 [Python Agent](../python-backend/06-python-agent.md)；通用工具/副作用约束见 [第 3 章](03-工具调用.md)，验收与受控观测分别见 [第 6 章](06-评估.md)、[第 7 章](07-失败模式与工程化.md)。

**误解靶子**：每一步后保存 JSON 文件就能保证不重复执行。保存前的外部副作用仍有崩溃窗口；聊天、记忆与交接工件都不能补出事务原子性或当前授权。

**判据**：在“外部成功、内部未记完成”处终止进程后，恢复能否得到唯一业务效果？

**自测**：只为这个崩溃窗口设计一条验收断言。具体后端实现继续读 [Go Agent 后端](../go-backend/06-Agent后端.md)。

## agent.protocol.interop：连得上之后还剩什么

**结论**：协议定义消息与能力表达；业务主体、授权范围、幂等与恢复仍需实现方约定和执行。

**案例**：两个服务都支持工具调用，但一个 `customer_id` 指全局客户号，另一个指租户内编号。JSON 都合法，结果却读错客户。换一个协议封装不会修复编号空间。

**机制**：分别核对传输/版本、消息/schema、身份/委托、业务语义四层。认证确定调用主体，不自动授予访问某对象的权限；能力声明也不证明所有实现支持同一扩展。协作任务需定义状态、工件、取消、重试和重复投递处理。MCP 与 A2A 解决的交互对象不同，不能把支持协议当成完整业务互操作。[MCP 版本规则](https://modelcontextprotocol.io/specification/versioning)、[A2A 规范入口](https://a2a-protocol.org/latest/specification/)

**误解靶子**：工具 schema 通过、OAuth 成功，调用就安全。对象归属与动作授权不由字段类型保证。

**判据**：收到一个格式合法但主体无权访问的对象 ID，执行前由哪一段确定性代码拒绝？

**自测**：为跨租户工具调用写出一个拒绝条件，不使用“模型应该知道”。

## agent.rag.evaluation：把检索失败拆开测

**结论**：检索系统需要分层证据，最终回答正确不能证明检索与引用都正确。

**案例**：回答来自模型已有知识，引用恰好指向无关段落。只看最终答案得满分，却不能证明更新政策后系统还会答对。

**机制**：冻结查询、文档版本、访问身份与标注证据。先检查可访问语料中有没有答案，再看召回候选是否包含证据、排序是否把证据送入上下文、生成是否受证据支持。Recall@k 要有已标注相关集合，MRR/nDCG 要说明排序标签；答案正确性与引用忠实度独立检查。评测加入无答案、相互冲突、过期事实与无权限文档；指标变化按同一批查询配对看，不能只比较两个总均值。[Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)、[RAG 引用忠实性研究](https://dl.acm.org/doi/10.1145/3731120.3744592)

**误解靶子**：回答错了就换 embedding；候选里没有证据时，rerank 无法凭空补回证据。

**判据**：出错查询的支持证据第一次消失在哪一层？先修这一层，再验证下游效果。

**自测**：已知证据不在 top-50、生成只看重排后的 top-5，指定应先检查的一个环节。
