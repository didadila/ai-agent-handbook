# 04 存储与检索：先有真相，再讨论加速

第 3 天**只必做一个 SQL 持久化验证改动**；本章索引、缓存、对象存储和检索扩展用于建立选型边界，后续逐项验证，不要求一天部署所有组件。片段是未执行教学示例，SQLite 与 PostgreSQL 差异不能靠换连接字符串消除。[官方证据](../../skills/knowledge-interviewer/references/domains/python-backend/sources.md)

## py.data.model — 把租户、状态机与版本写进数据模型

**结论**：任务表必须表达归属和合法迁移；Python 对象里的字段不能替代数据库约束。

**案例**：`get(task_id)` 忘记 tenant 条件，返回别人的检索结果；两个 worker 各自拿着旧任务对象，最后一次 `save()` 覆盖了已完成状态。

```sql
-- 教学 DDL 片段，非 demo 表结构承诺
CREATE TABLE tasks (
    task_id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    request_digest TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('pending','running','succeeded','failed')),
    version INTEGER NOT NULL DEFAULT 0,
    UNIQUE (tenant_id, idempotency_key)
);
```

**机制**：应用服务定义 `pending → running → succeeded/failed` 的迁移条件，数据库用唯一键、非空与检查约束挡住非法结构。`CHECK` 不自动限制从哪个旧状态转来；迁移使用带旧状态/版本/租约条件的 `UPDATE`，检查受影响行数。读取按 tenant + ID，生产 tenant 来自当前认证主体。结果、错误与审计字段也需要大小和敏感性边界。

**取舍边界**：SQLAlchemy 映射让代码易维护，但数据库约束仍是并发底线。修改状态枚举、字段或请求摘要算法需迁移与兼容旧 worker；不要把所有状态塞进无约束 JSON 并指望每个调用者自觉。

**误解靶子**：“只有 ORM 写库，所以不会出现坏状态。”并发、迁移脚本与新旧版本都可能绕过旧假设。

**判据**：按租户读取、重复创建、旧版本覆盖与非法状态是否被明确拒绝？是否检查条件更新的行数？

**自测**：旧 worker 在新 worker 完成后试图写 `failed`，你会把什么条件放入 UPDATE 来拒绝它？

## py.data.transactions — 短事务保护同库不变量，不跨网络兜底

**结论**：把必须一起成立的同库变更放在同一事务；不要在持有事务时等待模型、S3 或人工审批。

**案例**：任务已插入，事件记录插入失败却没有回滚；另一条路径把整个模型调用包在事务中，长时间占用连接与锁，提交请求开始排队。

```python
# 未执行标准库片段，conn 由调用者管理关闭
with conn:
    conn.execute(
        "INSERT INTO task_audit(task_id, event) VALUES (?, ?)",
        (task_id, "accepted"),
    )
    # task_audit 与任务的相关变更应使用同一 conn、同一事务
```

**机制**：事务提供所选数据库/隔离级别下的原子性与并发视图，不自动序列化所有业务决策。PostgreSQL 的隔离级别、行锁与条件更新需按不变量选择；冲突/序列化失败可能要重试完整短事务，不能只重试最后一句 SQL。外部调用的结果先取得，再用短事务提交；若存在不可消除的崩溃窗口，要设计幂等效果、Outbox 或对账。

**取舍边界**：SQLite 适合标准库单机 demo，多个连接也可能争用写锁；WAL 可改善读写并存，但 SQLite 仍非 PostgreSQL 式多写服务。演示 `database is locked` 不能推出 PostgreSQL 行锁吞吐，反过来也不能把 PostgreSQL 的 `SKIP LOCKED` 当成 SQLite 语法。

**误解靶子**：“用了 transaction，HTTP 超时也能一起回滚。”“SQLAlchemy session 就是一条全球串行通道。”事务边界不越过数据库，session 也不该跨并发任务共享。

**判据**：异常注入发生在两次写之间，是否都回滚？网络等待是否在事务外？提交结果不明时是否能查询而非盲目重放效果？

**自测**：任务创建必须与 Outbox 行同时落库，但发送队列消息要经过网络，事务应该在哪开始和结束？

## py.data.indexes — 索引服务真实查询形状，不能靠“建了很多”证明快

**结论**：按租户查询、领取待处理任务与恢复过期租约是不同访问模式，索引必须匹配过滤和排序。

**案例**：worker 每次 `WHERE status = 'pending' ORDER BY created_at LIMIT 1` 扫全表；只为 `task_id` 建索引，对领取队列没有帮助。

**机制**：先列出 SQL、基数与访问频率，再用目标数据库的执行计划检查扫描、排序和估计。可以评估 `(tenant_id, created_at)` 的租户列表索引、匹配 `status` 与时间的领取索引；PostgreSQL 可考虑部分索引，但受查询谓词与数据分布影响。唯一索引同时保护幂等约束，普通性能索引不保证业务唯一性。参数化 SQL 仍要关注计划与数据倾斜。

**取舍边界**：索引增加写放大、磁盘、维护与迁移成本；小表计划选择全表扫描未必是错误。教学 SQLite 用 `EXPLAIN QUERY PLAN`，生产 PostgreSQL 用自身计划工具；`EXPLAIN ANALYZE` 会真正执行语句，对写入须在受控环境防止副作用。本文没有运行计划，也没有声称性能收益。

**误解靶子**：“每列一个索引最保险。”“SQLite 本机很快，所以 PostgreSQL 无需测。”不同计划器、数据规模与并发会改变结果。

**判据**：每个索引是否对应一条重要查询？上线前是否在代表性数据下检查目标库计划、写延迟与索引创建方式？

**自测**：按 tenant 列最近任务和全局领取 pending 任务需要怎样的不同索引候选，为什么不只建 status 单列索引？

## py.data.cache — Redis 加速可重建读模型，不能承担事务真相

**结论**：任务终态、幂等映射与授权真相留在持久数据库；Redis 的命中只是一次可过期的观察。

**案例**：worker 先把 Redis 状态写成 succeeded，SQL 提交失败，前端短暂看到从未成立的成功；另一个缓存键只含 query，租户 B 命中了租户 A 的检索结果。

**机制**：cache-aside 先读缓存，未命中查权威库再填充；更新数据库后失效或按版本替换缓存，但数据库与 Redis 间有崩溃窗口，TTL、版本化键与重建降低不一致时间，不能制造跨库事务。键需包含租户、权限/文档版本、查询归一化与检索配置版本；敏感读取还要重新确认当前授权。缓存击穿可用有界请求合并，不能让缓存故障触发无限重试风暴。

**取舍边界**：第一版不用缓存通常最容易解释正确性。Redis 丢失时允许变慢，不应导致任务重复创建或凭空失去所有权。Redis 事务/Lua 的原子性只覆盖自身范围，不会与 PostgreSQL、队列或 S3 自动原子提交。授权撤销对缓存一致性要求往往高于普通内容更新。

**误解靶子**：“TTL 短就没有越权。”“Redis 是内存数据库，所以可当所有状态的唯一真相。”延迟与耐久/权限要求是不同选择。

**判据**：清空缓存后，任务与幂等行为是否仍正确？缓存键与值是否有租户边界和版本？失效失败能容忍多久？

**自测**：SQL 终态提交后 Redis 失效失败，如何让客户端最终读到新状态，同时不宣称强一致？

## py.data.objects — 对象存储保存大工件，签名链接是有期限的 bearer 能力

**结论**：数据库存归属、版本与对象引用；S3 存大文件。预签名 URL 的持有者在有效条件内可使用它，不能把链接当普通公开标识。

**案例**：检索结果带有报告下载预签名 URL，完整 URL 被写入日志；拿到日志的人不必登录服务就能下载。任务删除时只删 SQL 行，对象还留在 bucket。

**机制**：以不可变对象键/版本、摘要、大小、内容类型记录工件，下载前验证当前 tenant 权限，再签发短期、最小范围能力。AWS 访问密钥可用于签名请求，应像可行使权限的秘密保护；预签名 URL 本身是 bearer token，可能在签名期限之前因临时凭证过期等条件失效，不能默认可立即单独撤销。对象上传与数据库提交不是同一事务，采用“上传暂存对象 → 提交引用 → 回收孤儿”及对账。ETag 不总等于内容 MD5，例如 multipart 上传。

**取舍边界**：本地小 demo 可只存短文本，不需配置 S3。公共静态资源和私有任务工件要分 bucket/策略或明确权限边界；CDN 私有缓存、缓存键、URL 期限与删除传播需要独立验证。大工件直传减轻 API 流量，但上传大小、路径和覆盖权限仍须限制。

**误解靶子**：“URL 难猜就安全。”“数据库删了，S3 与 CDN 也就删了。”秘密泄露和多层存储不会自动收敛。

**判据**：日志是否去除签名参数？能否列出孤儿对象回收和撤权后已签 URL 的残余有效窗口？

**自测**：用户撤权时已取得十分钟下载 URL，服务现在能保证什么，怎样缩小后续泄露窗口？

## py.data.retrieval — 先保证租户过滤与引用版本，再优化召回质量

**结论**：检索索引是可重建投影；向量相近不代表被授权，也不代表答案得到证据支持。

**案例**：worker 先全局取 top-5 向量结果，再删掉其他租户，最后没有足够候选；更严重的是被删文档的摘要已先发给模型。旧 chunk 仍指向已替换文档，引用打不开。

**机制**：摄取链记录原文对象/版本、chunk ID、位置、切分器和 embedding 配置版本，检索链在支持的范围内先做租户/ACL 候选约束，再召回、可选重排与引用验证。若底层不能可靠前置过滤，须设计隔离集合/分区或更大的安全候选方案，并确保未授权文本永不进入上下文。SQL/全文索引适合结构化过滤和词项检索，向量检索处理语义相似，混合检索要有固定问题集证据。

**取舍边界**：小项目可用确定性词匹配 stub 验证流程与引用，不证明真实 embedding 的召回能力。先使用 SQL 管任务与文档元数据；是否增加 PostgreSQL 全文/向量扩展或专用检索服务，取决于规模、过滤、延迟和运维能力，不是五天必装项目。最终引用还要确认版本与当前访问权。

**误解靶子**：“向量库就是唯一知识真相。”“检索正确了，生成答案就一定正确。”召回、引用忠实性和生成事实性要分别测。

**判据**：固定问题集能否单独统计召回、租户泄露与引用可解析性？重建索引后是否仍能追溯原文版本？

**自测**：模型得到高相似度但已撤权的 chunk，应该在哪一层挡住，为什么仅在最终 UI 隐藏引用不够？
