# 07 运行与交付：分发正确还要能止损和恢复

本章把队列 worker、HTTP 反向代理多 worker、静态/CDN 与滚动发布放在同一张交付边界图里。案例为构造故障，指标示例不是实测值；本卷不提供真实部署，也不把本地 demo 视为生产就绪。[官方证据](../../skills/knowledge-interviewer/references/domains/python-backend/sources.md)

## py.ops.observability — 从受理到效果对账都能沿同一任务找证据

**结论**：观测必须区分受理、排队、执行、外部效果与查询；HTTP 成功率不能代替任务完成率。

**案例**：所有 POST 都快速返回 `202`，仪表盘绿色；worker 早已无法连接模型，pending 任务越来越老，用户从未拿到结果。只记录异常堆栈找不到具体任务在哪一段卡住。

**机制**：Python 结构化日志带 request/trace ID、task ID、受控 tenant 标识、attempt、租约版本或脱敏指纹（不记录可用于提交的原始token）、阶段、稳定 error code 与耗时；跨队列传播 trace 关联但验证元数据。记录受理率、拒绝率、最老队列年龄、活跃/过期租约、完成/失败、Outbox 积压、依赖 timeout、连接池等待与预算消耗。用任务状态时间戳分开排队与执行延迟，并定义测量窗口；不要把 task ID/原始 query 放成高基数指标标签。

**取舍边界**：第一版日志和少量计数即可；统一 tracing 逐步增加。正文不给“生产通用阈值”：应依据任务类型、负载与恢复目标制定告警。秘密、完整提示、原文、访问凭证和 S3 签名 URL 不进默认日志；采样与保留策略要兼顾成本及排障。不能靠补采日志恢复从未记录的效果状态。

**误解靶子**：“没 500 就没故障。”“全量日志越多越好。”异步失败与秘密泄露可能同时被忽略。

**判据**：给一个 task ID，能否查到受理、租约、尝试、终态和未知效果？worker 全停时，队列年龄告警是否能触发？

**自测**：提交延迟正常而用户等待持续上涨，你先看哪些阶段指标，如何区分下游慢、无 worker 和毒任务重试？

## py.ops.deployment — 四条分发通道各有容量与兼容边界

**结论**：队列消息、HTTP 请求、静态工件和新版本分发不能共用一个“多 worker 就好了”的解释。

**案例**：部署四个 API worker 后，全局 dict 被当成共享任务库，GET 命中不同进程就找不到任务；新版后端删除字段，CDN 上旧前端还在解析它；滚动替换时旧 worker 使用新 schema 写坏状态。

**机制**：

| 通道 | 要明确的保证与边界 |
|---|---|
| 队列 → job workers | 消息可重投、有限重试、租约/效果幂等；broker 和 SQL 不是一个事务 |
| 反向代理 → 多 HTTP workers | 每进程独立事件循环、内存与连接池；TLS、请求体上限、转发头信任范围、连接/读取超时与负载均衡 |
| 静态/CDN → 前端与下载者 | 带内容哈希的静态文件长期缓存；HTML/清单可更新；私有工件授权和签名不能混入公共缓存 |
| 滚动发布 → 新旧 API/job workers | readiness 控接单，停止领取后 drain；协议、消息与数据库 expand-contract 兼容；迁移有单独执行者 |

反向代理与应用 timeout 必须协调，避免代理先断开、任务却无追踪。SSE 若后续实现，还需验证缓冲、心跳与空闲超时。连接预算按全部 API/job 进程及副本求和，再考虑部署时新旧副本同时存在。

**取舍边界**：本地 CLI 无 HTTP/CDN/滚动部署，不能用其单进程测试证明这些能力。先做可回滚的小流量发布，观察任务与队列指标；不要让每个 API worker 在启动时各自跑非协调迁移或定时调度。自动回滚代码不等于回滚数据库破坏性迁移。

**误解靶子**：“sticky session 就是持久化。”“CDN 清缓存能同步所有客户端。”“容器重启就解决未知效果。”各自最多局部减害。

**判据**：新旧 worker 与旧前端能否共存？最大连接数是否含滚动重叠？停机时是否停止取新任务，并保留未完成任务可接管状态？

**自测**：数据库要新增必填字段，同时 CDN 仍可能服务旧 JS、队列还有旧消息，应怎样分步发布而不是一次删除旧字段？

## py.ops.recovery — 恢复演练验证数据库、索引与外部效果各自收敛

**结论**：重启只是恢复进程；业务恢复还包括接管、未知效果对账、备份还原与权限重新确认。

**案例**：恢复了任务库备份，检索索引仍指向较新的对象版本；旧任务再次发送通知。另一次重启把所有 running 改为 pending，旧 worker 恢复后又写回结果。

**机制**：定义 RPO（可接受的数据丢失窗口）与 RTO（可接受恢复时间），用实际备份还原演练验证，不把配置截图当证据。停止或隔离旧执行者后，按租约/token 规则接管；读取 checkpoint 时校验版本、当前授权与预算；对“已调用、结果未知”的效果查询/对账。权威数据库与原文对象建立可解释的一致恢复点，缓存清空重建，检索索引按版本重建并抽查引用。SQLite 备份使用其支持的备份方式，不能在活跃写入时只复制主文件而忽略 WAL 等状态。

**取舍边界**：单机 demo 可用临时数据库、显式崩溃点与假 clock 演示部分恢复；真实 PostgreSQL 备份、S3 生命周期/版本、broker 故障与多副本演练另做。恢复时不能把授权快照当当前权限；数据/对象删除及签名 URL 残留也要纳入安全计划。回滚软件仍可能需要前向修复数据与补偿外部效果。

**误解靶子**：“有备份就一定能恢复。”“最终一致就是以后自然会对上。”要有负责扫描、告警、处置与完成判据的人/程序。

**判据**：最近一次还原是否实际验证了租户查询、终态、引用版本与重复效果？演练报告是否写出未覆盖范围，而不是只写成功启动？

**自测**：恢复任务库后发现一次报告发送结果未知，应先重发、查询还是人工对账，依据什么选择，并怎样防旧 worker 再次推进？
