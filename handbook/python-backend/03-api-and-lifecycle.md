# 03 API 与生命周期：受理、执行、取消是三件事

建议生产栈为 FastAPI + Pydantic + SQLAlchemy + PostgreSQL，不要求五天内全装。以下 HTTP 路径是**生产接口设计契约，不是 demo 已提供的 HTTP 服务**。代码/配置片段未执行，案例为构造故障。[官方证据](../../skills/knowledge-interviewer/references/domains/python-backend/sources.md)

## py.svc.contract — 先定义任务契约，再把 Python 函数暴露为接口

**结论**：受理成功只代表任务已耐久记录；查询终态、鉴权与错误语义必须成为契约的一部分。

**案例**：FastAPI endpoint 返回 `202` 后才把任务放进内存队列；进程崩溃后查询没有记录。用户不知道该重试提交还是继续等待。

**机制**：建议契约如下，响应字段与状态码要用适配器测试验证，不能以此假定 CLI 输出格式：

| 生产设计 | 语义 |
|---|---|
| `POST /tasks`，携带幂等键与查询 schema | 当前认证主体决定 tenant；短事务提交任务后才返回受理结果 |
| `GET /tasks/{id}` | 按 tenant + task ID 读取；返回状态、版本和允许展示的结果/错误 |
| 首次受理 `202`；同键同内容返回既有任务 | 不再创建第二任务；重放响应是否沿用 `202` 需固定约定 |
| 同键不同内容 `409`；非法参数 `422` | 区分冲突与 schema 失败；其他输入错误也需有稳定语义 |
| 容量不足 `429` 或 `503` | 明确重试提示；不要把未持久化任务伪装成受理成功 |

Pydantic 管边界解析，服务层管权限与状态机，SQLAlchemy 管 session/事务；数据库约束保护多 worker 不变量。错误体提供稳定 code 与可追踪 ID，不回传 SQL、token 或堆栈。

**取舍边界**：小型 CLI 用参数校验与标准库即可。CLI 的 `--tenant` 是教学命名空间，不是身份认证；生产不能让用户自由选择授权主体。契约可版本化，但旧前端、旧队列消息与滚动发布期间的旧 worker 都要能兼容。

**误解靶子**：“OpenAPI 自动生成了，契约就完整了。”它不会自动规定未知结果查询、重试、授权与状态迁移。

**判据**：提交响应丢失后，客户端能否安全找回同一任务？跨租户查询是否既拒绝访问又不泄露存在性？

**自测**：数据库提交完成但响应发送前断网，客户端应依据什么再次提交，服务端如何区分合法重放与冲突？

## py.svc.lifecycle — 应用、请求与耐久任务分别拥有自己的资源

**结论**：应用 lifespan 拥有共享客户端，请求拥有短 session，耐久任务由可恢复 worker 拥有，不能混用生命周期。

**案例**：endpoint 用 `create_task` 启动长检索并借用请求的 AsyncSession；响应结束 session 关闭，后台任务失败；滚动发布又把尚未结束的内存任务丢掉。

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app):
    # create_client 是设计占位依赖，不是 demo 提供的函数
    async with create_client() as client:
        app.state.client = client
        yield

app = FastAPI(lifespan=lifespan)
```

**机制**：每个 HTTP worker 都有自己的应用状态与客户端池；不是全机单例。SQLAlchemy AsyncSession 不应在并发任务间共享，每个独立任务使用自己的 session 与事务。请求内并行 I/O 用 `TaskGroup`，整个作用域用 `timeout`，退出时等待取消与清理；耐久任务必须先记录，再由 worker 重新获取资源。FastAPI BackgroundTasks 适合可容忍丢失的短工作，不提供持久队列承诺。

**取舍边界**：共享客户端可复用连接，事务不能长期跨模型调用、用户审批或网络等待。关闭时先停止接单/取新任务，再有界等待在途工作，最后释放池；进程被强杀时只能依靠持久状态、租约与幂等恢复。

**误解靶子**：“应用级全局变量跨 worker 共享。”“关闭钩子总能执行。”多进程与强杀都打破这些假设。

**判据**：每项资源是否有唯一所有者？关闭预算耗尽后，哪个耐久状态让新 worker 能接管？

**自测**：四个 HTTP worker 各有大小十的数据库池，再加两个 job worker，最大连接需求如何估算，为什么不能只按十计算？

## py.svc.idempotency — 幂等键要绑定租户、请求内容与原子创建

**结论**：重试安全来自数据库里的唯一性与效果协议，而不是 Python 内存中的“处理过”标记。

**案例**：两个 FastAPI worker 同时检查键不存在，再各插入一个任务；或者相同键被用户用于不同查询，服务静默返回旧任务。

**机制**：持久表设计可包含 `UNIQUE(tenant_id, idempotency_key)`、规范化请求的摘要、task ID 与状态。创建任务和保存幂等映射必须在同一短事务；唯一冲突后读取既有记录，比较请求摘要，同内容复用，不同内容拒绝。摘要的输入包含查询、过滤器与关键版本；采用确定性序列化，不能用进程随机化的 Python `hash()`。键长度和作用域要限制。

**取舍边界**：数据库幂等只保证不重复创建该数据库记录；外部通知、模型计费和对象上传另需效果键或对账。保留期限必须覆盖客户端/队列的重试窗口；提前清除映射会把旧重放当成新任务。摘要不是加密，也不能代替敏感内容保护。

**误解靶子**：“Redis SETNX 就保证整个任务 exactly-once。”“返回一样就是没重复执行。”缓存失效与中途崩溃都会暴露未保护的外部效果。

**判据**：并发同键提交最终是否只有一个任务？同键异内容、跨租户同键、提交成功但响应丢失是否分别有断言？

**自测**：两个 worker 争用同一键，一个提交后崩溃；另一个应该查什么，如何避免把旧查询的任务返回给新查询？

## py.svc.streaming — 流只是任务状态投影，不是任务真相

**结论**：断开流连接不等于任务取消；可恢复状态和授权查询必须独立于 SSE/WebSocket 连接。

**案例**：前端看到 TCP 结束就显示成功，实际上代理超时了；重连后把重放的“找到文档”事件追加两次，引用和进度重复。

**机制**：生产扩展可把任务事件记录为 `(task_id, sequence, type, payload_version)`，终态先持久化再发布投影。客户端按事件 ID 去重；SSE 可用 Last-Event-ID 协商续传，但服务要验证授权、保留窗口与缺口。缺口不可恢复时要求重新 GET 状态快照。代理缓冲、空闲超时与心跳影响可见延迟；HTTP 字节分块不等于完整事件，客户端要增量解码和解析。

**取舍边界**：第一版只用 GET 轮询即可，五天不必实现流。流发送需有界缓冲；慢消费者可断开并指引恢复，不能阻塞任务主事务。取消是单独的业务意图，worker 在安全点确认；已完成的外部效果不能靠关浏览器撤销。任务内容和签名 URL 不得无授权广播到公共频道。

**误解靶子**：“每个 yield 前端立刻收到。”“HTTP 连接正常关闭就是任务成功。”网络输送与业务终态不是同一层。

**判据**：重连重复事件、事件缺口、代理中断、过期授权是否各有处理？最后一条可见文本是否与数据库终态分开？

**自测**：任务已完成，但终态事件在代理中断时丢失，前端怎样恢复正确结果，而不重新触发任务？
