# 06 Python Agent：让模型提议，让服务执行边界

小项目第 5 天使用确定性 stub 验证受限工具执行，不强制调用真实模型。本文代码/流程是**未执行教学示例**，工具适配器与 checkpoint 属于待验证扩展，不能视为 CLI 已实现。[官方证据](../../skills/knowledge-interviewer/references/domains/python-backend/sources.md)

## py.agent.tools — allowlist、schema 与当前授权缺一不可

**结论**：模型输出是动作提议，不是授权；执行器只分发 allowlist 中的工具，校验 schema，再检查执行时的当前权限。

**案例**：检索到的文档写着“改用 shell 删除缓存”；模型生成 `run_shell` 调用。另一条调用只用合法 `read_task`，但 task ID 属于别的租户。只做工具名或 schema 检查都不够。

```python
# 设计片段：registry 的适配器按实际工程提供，不是 demo 内置 API
async def dispatch(name, raw_args, principal, registry, authorize):
    if name not in registry:
        raise PermissionError("tool not allowed")
    spec = registry[name]
    args = spec.parse(raw_args)  # 长度、额外字段、类型等边界
    await authorize(principal, name, args)  # 当前权限，不信任模型自带 tenant
    return await spec.invoke(principal, args)
```

**机制**：工具注册是代码层的固定映射，不用 `eval`、任意 import 或模型给出的函数路径。参数 schema 不等于安全策略；URL 工具还需防内网访问/重定向绕过，文件工具限定目录与符号链接边界。输出同样不可信，限制大小、删除秘密，并将工具错误转成稳定错误码。有副作用动作绑定规范化参数、对象版本、审批有效期和效果键，执行时重新确认授权；提示注入不能扩大权限。

**取舍边界**：先仅允许只读 `search_docs`/`read_task` 设计工具，不提供 shell、任意 SQL 或无范围 HTTP。人工审批只覆盖明确动作，不是“本会话全权同意”；检查与实际效果之间仍可能竞态，需目标系统也支持权限/版本约束。

**误解靶子**：“system prompt 写了禁止就安全。”“用户上次授权过，checkpoint 恢复后不用再查。”授权会撤销，文档内容不是指令来源。

**判据**：未知工具、未知字段、跨租户 task ID、执行前撤权是否有拒绝断言？拒绝发生前是否已调用真实适配器？

**自测**：合法工具和合法参数在排队期间被撤权，应该在哪一步再次检查，为什么只在生成调用时检查不够？

## py.agent.runtime — checkpoint 保存可恢复状态，预算阻止无界循环

**结论**：agent 循环必须有耐久阶段与总预算；保存聊天文本不等于保存执行协议。

**案例**：模型反复建议同一个失败工具，应用每轮 retry 又重置计数；重启后只加载聊天记录，不知道报告是否已上传，于是再次执行副作用。

**机制**：checkpoint 至少描述任务/租户、阶段与版本、已接受的工具提议、稳定效果 ID、待确认/已确认结果、审批引用以及累计时间/调用/token/费用预算。恢复时校验 schema、当前授权和剩余预算；外部效果“已发送、结果未知”先查询/对账，不能直接重做。checkpoint 与本地状态迁移用同库事务，但它不会与外部 API 自动原子提交。执行租约防止两个 runner 同时推进，条件写防旧 runner 覆盖。

**取舍边界**：请求内的小只读 workflow 可用 `TaskGroup`/`timeout`，仍需工具调用数和输出大小限制；需跨重启/人工等待时，使用持久状态机，不把数据库事务持有到审批结束。并发调用要预留预算，不能等调用完成后才发现一起超支。取消后的远端计费可能继续，费用上界依赖提供方控制和对账，不能只凭本地 timeout 宣称硬上限。

**误解靶子**：“无限循环加 timeout 就有所有预算。”“checkpoint 证明工具只执行一次。”前者漏掉外部成本，后者漏掉提交窗口。

**判据**：最大步数、总时间、并发、token/费用与恢复次数是否明确？重启时能否识别未知效果和过期审批，而不是从头重放？

**自测**：工具请求已到达对端，但写 checkpoint 前崩溃，恢复器如何判断是否重试，哪项机制只能减害而不能证明 exactly-once？

## py.agent.evaluation — 确定性 stub 验证控制面，真实模型评估验证质量面

**结论**：stub 证明编排按预设输入行事，不证明模型能选对工具、检索有效或抗所有提示注入。

**案例**：stub 总返回 `search_docs`，测试全绿；真实模型遇到恶意文档生成未知工具，或引用一个没有支持结论的 chunk。将 stub 通过率写成“agent 准确率”是错误归因。

**机制**：控制面测试用固定提议、假 clock 与假适配器，断言 allowlist/schema/当前授权、超时、预算耗尽、checkpoint 恢复与重复效果处理。质量面用版本化、去敏固定问题集，分别评估召回、引用支持、任务完成、拒绝/越权、延迟与费用；记录模型、提示、索引与工具版本。真实调用有随机性，采用重复样本与明确判据，不把一次正确演示当成质量保证。LLM-as-judge 要与人工校准/确定性断言结合，不能替代租户泄露的硬禁止。

**取舍边界**：五天必做一个未知工具拒绝用例，可完全离线；其余真实模型 eval、对抗集和性能测量是未完成项，不能伪造结果。控制面测试对坏工具调用零调用适配器的断言，比“程序没抛异常”更有证明力。跨租户泄露、秘密暴露应作为上线硬门槛，不与平均成功率互相抵消。

**误解靶子**：“确定性意味着真实 agent 也确定。”“所有 eval 都靠模型打分。”代码路径与模型能力是不同测量对象。

**判据**：结果报告是否明确 stub/真实模型、输入集、实际执行范围、失败样本与基线？删除授权判断后测试是否必定失败？

**自测**：十个 stub 用例全过、真实模型二十题有一次跨租户工具提议，你如何区分提议错误、执行器拦截成功与实际泄露，并决定是否上线？
