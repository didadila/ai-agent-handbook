## py.eng.dependencies — 声明依赖不等于可复现安装

**结论**：`pyproject.toml` 只描述允许的依赖范围；要复现同一套包，还要锁定完整解析结果并固定构建产物。

**案例**：构造案例：开发机声明 `requests>=2.28`，今天解析到 2.31；CI 缓存过期后解析到 2.32，某个传递依赖改变了默认超时。测试仍绿，部署后外部调用开始超时，团队说“代码没变”。

**机制**：`[build-system]` 声明构建后端及其依赖，`[project]` 声明名称、版本、`requires-python`、运行依赖与可选依赖；它本身不定义锁文件。安装器按版本范围、Python 版本与平台标记解析依赖；冲突时可能报 `ResolutionImpossible`，并回溯尝试其他版本组合，解析结果会随索引内容与时间变化。锁文件（例如 `pylock.toml`）记录完整依赖图、版本与哈希，用于可复现安装；只有所有传递依赖都被固定时，普通 requirements 文件才有接近的效果。构建一次 wheel，让测试与部署提升同一产物，生产机不再从源码重新解析。`src/` 布局可减少“从当前目录误导入未安装代码”的假通过。

**取舍边界**：全部钉死提高复现性，但延迟安全更新，需要定期升级与回归；不同操作系统可能选择不同 wheel，锁相同也不等于文件相同；私有索引需要认证，凭证不能进仓库；锁文件不覆盖解释器、系统库、构建工具与运行环境。

**误解靶子**：“写了 `pyproject.toml` 就有锁”“`pip install` 成功就说明部署环境一致”“把 venv 打包过去最可复现”“只锁顶层包就锁住了传递依赖”。

**判据**：干净机器能否只凭声明/锁与固定 Python 版本重建同一 wheel？依赖变更是否经过评审与测试？生产是否使用构建一次的同一位移产物？

**自测**：同一仓库今天和下周装出不同的传递依赖版本，先补哪类记录，为什么只固定顶层包不够？

## py.eng.testing — 测试要证明失败路径，且不共享隐式状态

**结论**：测试的价值来自可重复的隔离、明确的替身边界和对失败路径的断言，不是覆盖率数字。

**案例**：构造案例：两个用例单独运行都通过，一起运行时第二个读到第一个留下的模块级缓存；另一个用例依赖真实时钟和网络，白天通过、夜里失败。覆盖率显示 100%，但没有任何用例覆盖重复提交。

**机制**：pytest fixture 有 function、class、module、package、session 五种作用域；function 给每个测试独立实例，session 适合昂贵只读资源；yield 之前是 setup，之后是 teardown，测试失败也会执行清理。`monkeypatch` 与 `unittest.mock.patch` 在作用域结束时恢复；patch 要打在“被查找的命名空间”，不是定义处，`create=True` 甚至能对不存在的 API 造出通过测试。替身要分层：stub 返回固定值，fake 是可工作的内存实现，mock 断言交互；验证业务行为优先用 fake/stub，过度 mock 会把测试绑到实现细节。时间、随机数、ID、网络和文件系统都从边界注入；假时钟显式推进，不用 sleep 等真实时间。异步测试要保证每个测试自己的事件循环并清理未完成任务，用受控事件同步而不是依赖毫秒级调度。

**取舍边界**：更多真实依赖能发现集成问题，但更慢也更不稳定；全 mock 快，却可能测不到契约变化。fixture 作用域越大越省时间，也越容易共享可变状态。覆盖率只说明哪些行被执行，不证明断言有效；变异测试只探测被注入的故障，也不证明所有故障都被覆盖。失败后重跑才通过的用例仍要计入分母，不能只报最终绿色。

**误解靶子**：“覆盖率 100% 就没 bug”“mock 越多越隔离”“单独通过就等于整套稳定”“重跑直到绿就是通过”。

**判据**：测试能否单独、重复、并行运行而不互相污染？失败路径、权限拒绝、超时和重复提交是否有断言？替身是否只替换边界，而不是替换被测逻辑？

**自测**：两个用例单独通过、一起失败，先查哪一类原因？

## py.eng.errors — 先分类错误，再决定是否重试

**结论**：只有“可能暂时失败且操作可安全重复”的错误才值得重试；其余错误应快速失败、修正输入或查询未知结果。

**案例**：构造案例：下游 400 校验错误被通用重试包重试三次；数据库死锁重试没有上限；上游整体超时后，每一层各自重试，放大四倍请求。

**机制**：先分类：输入、权限、不存在属于永久错误；冲突、限流、连接失败可能是暂时错误；超时或连接中断属于“结果未知”，不能当失败盲目重放。领域错误与基础设施错误分开，在边界映射为稳定错误码/状态，不把堆栈和 SQL 文本返回客户端。重试需要幂等依据（天然幂等，或幂等键/稳定效果 ID），并有次数上限、指数退避加抖动、总期限与调用链共享的重试预算；尊重下游的 `Retry-After`。期限要传播：下游拿到的剩余时间小于上游总期限，单次尝试超时小于总预算。取消与超时不同，`CancelledError` 不能被吞掉。TaskGroup 失败会取消同组任务，`ExceptionGroup` 需要分组处理，不能只捕获第一个异常。

**取舍边界**：重试提高瞬态成功率，也会在下游过载时放大流量；退避降低压力但增加尾延迟；断路器保护下游，却可能误拒绝正在恢复的请求；不是所有超时都能安全重试。错误码过粗会丢失诊断信息，过细又会把内部实现暴露给客户端。

**误解靶子**：“所有异常都重试三次”“超时说明没执行”“重试越多越可靠”“捕获 Exception 就统一处理”。

**判据**：每个重试点是否有幂等依据、次数/期限/退避上限？未知结果是否先查询或对账？错误是否映射为稳定码并保留可观测信息？

**自测**：下游调用超时后，直接原样重试三次，最坏会制造什么后果？

## py.eng.time — 时间要有参照系，金额要有精度

**结论**：持久化用带时区的 UTC 时间，测持续时间用单调时钟，金额用十进制定点；三者不能互相替代。

**案例**：构造案例：租约到期用 `time.time()`，运维校时后系统时钟回拨，租约提前或延后失效；API 返回不带偏移的 ISO 字符串，客户端按本地时区解释；金额用 float 累加，对账差一分钱。

**机制**：`datetime` 分 naive 与 aware：aware 能定位到具体时刻，naive 的解释依赖程序；naive 与 aware 做大小比较会抛 `TypeError`，相等比较为 False。持久化存 UTC aware，展示时再转换。`time.time()` 是墙钟，可能因校时回拨；`time.monotonic()` 不会倒退、不受系统时钟更新影响，但参考点未定义，只能在同一进程内比较差值，不能持久化后跨进程比较。租约与超时的进程内经过时间用单调时钟；跨进程持久期限要约定时钟来源与容差，并接受墙钟跳变风险。日期与时间不同：生日是 date，事件是 datetime；夏令时存在不存在和重复的本地时刻，使用 `zoneinfo` 并明确策略。金额不能用 float：多数十进制小数无法精确表示，误差会累积；用 `Decimal` 并显式量化/舍入，或存最小货币单位的整数，数据库列与序列化格式一起固定。JSON 没有 datetime/Decimal 原生类型，要定义统一编码（例如带偏移的 ISO-8601、字符串十进制），并拒绝 NaN/Infinity 等非标准值。

**取舍边界**：全 UTC 便于比较但不便展示；Decimal 精确但比 float 慢、需要上下文；单调时钟适合测间隔，不适合审计时间；跨进程期限仍要处理时钟漂移。存字符串可读，存整数/时间戳更利于比较，两者需要明确转换契约。

**误解靶子**：“`datetime.now()` 就是 UTC”“ISO 字符串不带时区也没关系”“float 足够存金额”“monotonic 可以持久化后跨进程比较”。

**判据**：所有持久时间是否 aware UTC？持续时长是否用单调时钟？金额是否有精度、舍入与币种契约？JSON 边界是否有明确编码与拒绝规则？

**自测**：租约到期判断应该用墙钟还是单调时钟，为什么不能把单调值存库后跨进程比较？

## py.eng.security — 认证、授权和租户是三道不同的门

**结论**：认证回答“你是谁”，授权回答“能否对这个资源做这个动作”，租户隔离要求每次数据访问都从当前主体推导范围。

**案例**：构造案例：CLI 的 `--tenant` 被当成身份；schema 校验通过后直接按请求体 tenant 查询；URL 工具允许访问任意地址，攻击者用内网元数据地址读取凭证；上传文件名 `../../etc/passwd` 被直接拼接。

**机制**：认证建立主体（session、token、mTLS），授权按主体、动作、资源和租户在服务端检查，默认拒绝、最小权限；客户端隐藏按钮不是授权。租户来自认证主体，不来自可伪造的请求字段；异步任务、重试和恢复时要重新确认当前授权，不能沿用提交时的快照。输入要限制结构、长度、大小、字符集并做规范化；SQL 用参数绑定，ORM 也不能替代授权；动态排序和表名走白名单。SSRF 防护优先目标 allowlist；动态目标要阻断私有、回环、链路本地和元数据地址，解析后校验 IP 并固定，禁用或逐跳校验重定向，出口网络最小化。文件路径要规范化、解析符号链接并限定根目录，不信任扩展名或 MIME，压缩包防 zip slip。不可信输入禁用 pickle：官方文档明确恶意 pickle 可在反序列化时执行任意代码，JSON 等格式更合适；YAML 使用 safe_load。秘密通过环境或秘密管理器注入，不进仓库、日志和错误响应；日志对 token、查询内容和租户数据做受控脱敏。锁与哈希、私有索引和依赖审计降低供应链风险，但不等于依赖代码可信。

**取舍边界**：严格 allowlist 会影响合法动态目标；每次请求查授权增加延迟，可以缓存，但必须有失效与撤权传播；脱敏降低可诊断性，需要受控快照；租户隔离增加查询条件与索引设计成本。安全控制要覆盖同步请求、后台任务和恢复路径，不能只做入口。

**误解靶子**：“schema 合法就有权限”“内网地址天然可信”“JWT 签名通过就代表当前仍有权限”“用了 ORM 就没有注入”“日志里放 token 方便排障”。

**判据**：认证主体是否唯一来源？每个资源访问是否有服务端授权与租户条件？SSRF、文件与反序列化边界是否有拒绝用例？日志与错误是否泄露秘密？

**自测**：接口从请求体读取 `tenant_id` 并直接查询，这属于认证、授权还是租户隔离问题？

## py.eng.profiling — 先测量瓶颈，再决定加什么

**结论**：性能问题要先用目标环境的延迟、CPU、内存和排队证据定位，不能靠“加线程、加缓存、换框架”猜。

**案例**：构造案例：接口 p99 升高但 CPU 只有 20%，团队把线程数翻倍，数据库连接池等待更严重；另一个接口内存持续上涨，实际是无界缓存保留了大 payload。

**机制**：先分层测量入口延迟分位（p50/p95/p99）、排队时间、执行时间、下游时间和连接池等待；平均值会掩盖尾延迟。CPU 侧，`cProfile` 做确定性函数调用统计，有事件记录开销，不适合当基准；采样 profiler 适合长驻服务但可能漏掉短调用。要区分 CPU-bound、I/O-bound 和锁/池争用。内存侧，`tracemalloc` 追踪 Python 分配，比较两次快照找增长点；它不包含启动前分配，C 扩展分配也可能不在默认域，RSS 上涨还要排除分配器和缓存。数据库侧，统计查询次数发现 N+1，查看执行计划与索引，限制返回列、行数和 payload 大小，必要时分页或流式处理。容量上，worker/线程/协程数乘以每请求并发不能超过下游连接上限；利用率接近饱和时排队延迟非线性上升，可以用 Little 定律估算在途请求。优化一次只改一个变量，用相同负载与数据复测；微基准不能直接外推生产。

**取舍边界**：profiler 有开销、采样有盲区；缓存降低延迟但引入一致性与内存成本；增大连接池提高并发但加重数据库争用；更多 worker 受 CPU、内存与连接预算限制。没有基线数字时，任何“更快”都只是感觉。

**误解靶子**：“CPU 不高就不是性能问题”“加线程一定更快”“平均延迟正常就没有尾延迟”“缓存总能提速”“本地微基准等于生产容量”。

**判据**：是否有目标环境的分位延迟与资源证据？瓶颈在 CPU、I/O、锁、池还是下游？优化前后是否同负载复测并记录？

**自测**：接口 p99 很高但 CPU 使用率很低，先查哪一类等待，而不是直接加线程？
