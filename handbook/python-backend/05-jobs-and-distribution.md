# 05 任务与分发：重复、丢失和接管都要有协议

“分发”既包括任务队列，也包括 HTTP 反向代理多 worker、静态/CDN 与滚动发布；后三者在第 7 章展开。本章不要求安装 Celery 或 broker。片段为未执行教学示例，CLI 是本地持久化实验，不是多机队列实测。[官方证据](../../skills/knowledge-interviewer/references/domains/python-backend/sources.md)

## py.jobs.delivery — ack 与 retry 决定重放窗口，不能消除重复效果

**结论**：将队列投递视为可能重复且可能延迟；处理成功和消息确认之间总有故障窗口。

**案例**：worker 完成检索并写结果后，确认前崩溃；消息重投。如果 handler 直接追加结果或重复发通知，就出现第二次效果。反之，执行前就确认，崩溃可能让任务没有机会重新投递。

**机制**：Celery 的 early/late ack、`acks_late`、`task_reject_on_worker_lost`、prefetch 与 retry 必须根据任务、broker 和失败类型配置，并验证真实行为。late ack 并不保证任何 worker 退出都重投；启用 worker-lost 重入也可能制造永久失败的循环。`retry` 可能发布新消息，不能据此推导 exactly-once。可靠策略是稳定 task/effect ID、幂等 handler、持久终态、有限重试与死信/人工处置。

**取舍边界**：短、可重放任务适合队列；长任务还要分阶段、heartbeat 与接管。broker ack 不等于数据库 commit，超时不能判断外部是否已执行。本地 SQLite worker 能演示持久任务与重启，但不验证 broker 可见性期限、网络分区、Celery 配置或集群吞吐。

**误解靶子**：“acks_late + retry 就 exactly-once。”“重试只会补做没成功的部分。”未知外部结果必须查证。

**判据**：注入“结果提交后、ack 前”崩溃，重复执行是否只保留一个业务效果？毒消息是否有限终止而不是无限消耗配额？

**自测**：模型请求超时后队列重试，如何避免重复通知和无界计费，为什么只保存 Celery task ID 还不够？

## py.jobs.outbox — 任务记录和待发事件必须同库同事务

**结论**：Outbox 封住“已创建任务却没留下待发消息”的窗口；发送端仍可能重复发送。

**案例**：服务先提交 PostgreSQL 任务，再向 broker 发布，网络中断后无人知道这个任务该入队。把 Outbox 放到另一个数据库同样留下双写窗口。

**机制**：在同一个数据库、同一个事务/连接中写任务与 Outbox 行：包含稳定 event ID、task ID、payload 版本和待发送状态。独立 relay 领取记录、发布消息，成功后标记已发送；如果发布成功而标记失败，下次仍会发布，所以消费者按 event/task/effect ID 幂等。relay 可以用租约或目标库支持的锁来并发领取，不能长期持锁等待网络。

```python
# 设计片段，未执行；SQL/表名不是 demo 接口
with conn:
    create_task_row(conn, task_id, tenant, digest)
    create_outbox_row(conn, event_id, task_id, payload_version=1)
# relay 在事务之外发布；发布与标记之间存在可重放窗口
```

**取舍边界**：如果本地 worker 直接轮询同一任务表，不跨库发布消息，第一版不必为教学强加 broker 与 Outbox。增加独立 broker 后才明确引入 relay、积压监控、保留期限与对账；Outbox 不是“两边同时提交”的分布式事务，也不保护所有外部副作用。

**误解靶子**：“用了 Outbox 就不会重复消息。”“在代码里连续调用两个提交也叫同事务。”数据库边界与发送重放仍需说明。

**判据**：任务与 Outbox 是否共用一次提交？relay 重启后是否继续未完成发送？消费者重复 event ID 是否不产生新效果？

**自测**：relay 发布成功后进程被强杀、还没标记 sent，恢复时应当怎么做，重复的代价由谁限制？

## py.jobs.leases — 租约到期允许接管，旧 worker 的外部效果不能自动撤销

**结论**：租约给 worker 临时写入资格；版本/token 防旧持有者落库，外部效果还需要幂等或对账。

**案例**：worker A 暂停超过租约期限，B 接管并完成；A 恢复后仍持旧 Python 对象，试图覆盖终态，甚至再次发送通知。

**机制**：短事务原子领取 pending 或租约已过期的 running 任务，更新 owner、轮换唯一 lease token（外部支持顺序栅栏时使用单调递增版本）、设置到期时间；并发下检查条件 UPDATE 的行数。本地实验使用不透明随机token做当前持有者相等检查，不把它当作可排序的外部fencing版本。心跳与终态提交都必须带 owner/token 和有效期限条件。PostgreSQL 可按设计使用行锁/`SKIP LOCKED`，SQLite demo 应采用自己的事务与条件更新，不能照搬语法。持久期限采用约定的时钟来源；进程内 timeout 可用单调时钟，但单调值不能直接跨进程持久化比较。

**取舍边界**：过短租约增加误接管，过长租约延长恢复。失去租约的 worker 不再提交结果，但底层线程或远端请求可能仍运行。fencing token 只有外部系统也检查并拒绝旧 token 才能挡住外部写；否则用稳定效果键、查询外部结果或对账。锁住一条 SQL 行不能保证一次模型计费。

**误解靶子**：“租约过期证明旧 worker 已死。”“fencing token 写在日志里就有效。”暂停/网络分区不等于停止，令牌要被写入端强制验证。

**判据**：人工推进 clock 后能否接管？旧 token 的完成写是否被拒绝？外部调用重复或结果不明是否有恢复记录？

**自测**：A 的租约过期后已把报告上传，B 又上传同一报告，SQL token 能防哪部分，对象存储重复效果要怎样处理？

## py.jobs.scheduling — 领取、公平、退避与停机是一张容量账

**结论**：调度不仅是定时触发；它要决定谁先执行、失败何时再试、谁不能饿死，以及停机后如何接续。

**案例**：大租户一次提交大量任务挤满 worker，小租户等待超时；坏查询每秒重试，数据库与模型调用被同一任务占满。滚动发布时旧 worker 停不下来，新 worker 又重复领取。

**机制**：持久任务记录 `attempt`、`next_run_at` 与有限失败原因，按策略领取可运行项；可用指数退避加 jitter 避免同步重试，明确永久错误不重试。租户活跃数和排队数分别设上限，优先级策略需防饥饿。周期任务在重启时可能漏跑或补跑，明确是跳过、合并还是按 occurrence ID 幂等补偿；不要让多个 HTTP worker 各自启动同一个无协调 scheduler。

**取舍边界**：第一版单 worker、固定上限与有限重试足够；公平队列、定时调度与多机协调逐项选学。停机先停止领取，允许在预算内完成或归还/过期接管；清除 running 记录来“解锁”会破坏审计与外部效果追踪。重试预算要与 agent 时间/费用预算合并，而非每层各无限重试。

**误解靶子**：“多加 worker 就不会堵。”“cron 只会触发一次。”下游容量、租户公平与重复调度都没有被处理。

**判据**：是否有队列年龄、租户活跃数、attempt 上限与永久失败出口？滚动停机期间谁仍可领取，怎样防重复周期任务？

**自测**：模型提供方限流十分钟，你会如何安排退避、租户公平和总预算，为什么不让所有失败任务立即重试？
