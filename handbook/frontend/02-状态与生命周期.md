# 第 2 章 状态与生命周期

依赖：第 1 章的值、作用域、异步与运行时契约。三个问题依次是：谁还能提交结果、任务事实在哪里、组件如何投影这些事实。

## fe.web.lifecycle —— 清理资源，还要拒绝过期提交

### 结论

为请求和订阅规定所有者、有效期与清理路径；提交结果时再次检查它是否仍属于当前视图。

### 案例

用户在 A 会话发起检索，马上切到 B。B 的结果先返回，随后 A 的响应覆盖了 B。请求加过 debounce，组件也没有报错，但展示内容已串会话。

### 机制

防抖减少启动次数，不给已发请求排序。为查询分配会话标识与 revision；回调提交时核对当前 scope，旧 revision 直接丢弃。切换时 abort 请求、取消 timer、解除监听、关闭 EventSource、释放对象 URL；即使请求已完成或不能被取消，revision 检查仍有效。清理应可以重复调用，不应关闭新 owner 刚建立的连接。[React 的乱序清理示例](https://react.dev/reference/react/useEffect#fetching-data-with-effects)、[AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)

```js
let revision = 0;
async function search(query) {
  const mine = ++revision;
  const result = await fetchResults(query);
  if (mine !== revision) return;
  show(result);
}
// 切会话时也必须递增 revision；真实实现同时清理旧资源。
```

### 误解靶子

“abort 旧请求足够了。”已有完成回调、自定义不可取消工作和切换竞争仍可能尝试提交。

### 判据

旧会话的任意回调还能否修改当前会话的状态？

### 自测题

1. A 后发完成、B 先完成时，只写出允许提交的 revision。
2. 给一个长期订阅指定唯一的资源所有者。

## fe.state.task —— 连接状态不能冒充任务状态

### 结论

服务端任务状态、传输状态和本地编辑状态分开维护；断网代表失去观测，不代表任务完成或取消。

### 案例

聊天页只用 `isLoading`。流关闭时设成 false，然后显示“已完成”。实际上连接在工具执行期间断开，后端仍在退款。用户点击重新生成，重复提交了业务动作。

### 机制

用不同字段表达不同事实，并定义允许的转移。页面刷新后读取服务端快照，再从快照对应游标续流。快照要携带 `last_seq` 或等价版本；获取快照与订阅之间的事件缺口由服务端重放契约覆盖。终态由权威事件/快照确认，不能由“没有更多字”推断。乐观更新记录 operation ID 和待确认状态；失败撤销对应操作，不能恢复整份旧快照覆盖后续成功修改。

| 状态域 | 示例 | 事实来源 |
|---|---|---|
| 任务 | queued/running/waiting_approval/completed/failed/cancelled | 服务端 |
| 本地操作意图 | cancel_requested/等待提交结果 | 客户端记录；不冒充服务端已接受或已取消 |
| 连接 | connecting/live/reconnecting/offline | 客户端传输层 |
| 编辑 | clean/dirty/saving/conflict | 本地输入与保存响应 |

以上状态名是本书应用契约，不是通用协议标准。客户端缓存和 reducer 不代替持久任务运行时，见 [Agent 耐久执行](../ai-agent/09-架构与运行时补全.md)。

### 误解靶子

“按钮能点了就是任务结束。”“关闭页面等于取消任务。”它们都只说明本地 UI 变化。

### 判据

拔网线后页面是否仍能表达“最后已知为运行中，目前状态未知”？

### 自测题

1. 只为“已请求取消但服务端未确认”命名一个状态。
2. 快照为 seq=40 时，只说明续流应从哪个位置开始。

## fe.render.react —— 渲染快照与组件身份

### 结论

React 的回调属于某次渲染快照；组件身份决定状态保留，Effect 用于同步外部系统并承担清理。

### 案例

流订阅回调执行 `setText(text + delta)`，多次回调都读到建立订阅时的旧 text，消息只剩最后一块。另一个页面用数组下标作 key，删除第一条后，第二条编辑框继承了第一条草稿。

### 机制

| 现象 | 机制与处理 |
|---|---|
| 多次更新依赖旧值 | 对相同 state 的累计更新使用 `setText(previous => previous + delta)`；跨消息隔离仍按 ID 完成 |
| 列表项继承别人的输入 | key 与类型/位置共同决定身份；使用稳定消息 ID，不在 render 中随机生成 |
| 双订阅 | Effect cleanup 与 setup 对称；开发环境且根部启用 Strict Mode 时，初次挂载有额外 setup→cleanup→setup 检查。仅在子树启用时，不额外重跑初次挂载的 Effect；不要推广成所有环境必然两次 |
| 依赖变化不重连 | Effect 声明读取的响应式依赖，不靠禁用检查制造“只执行一次” |
| hydration 不匹配 | 服务端 HTML 与客户端首次渲染应一致；浏览器专属数据放合适的客户端阶段，而非初始 render 直接读取 |

state 驱动可见内容；ref 保存不需触发重绘的可变句柄，不把可见状态藏进 ref。派生数据能直接计算时，不额外用 Effect 复制一份。[状态快照](https://react.dev/learn/state-as-a-snapshot)、[身份](https://react.dev/learn/preserving-and-resetting-state)、[Effect](https://react.dev/reference/react/useEffect)、[StrictMode 的边界](https://react.dev/reference/react/StrictMode)、[hydration](https://react.dev/reference/react-dom/client/hydrateRoot)

### 误解靶子

“把依赖数组设为空就解决重复调用。”这可能把旧会话、旧回调永久锁进订阅。

### 判据

在切会话、重排列表、setup→cleanup→setup 三种变化后，是否仍只有正确身份的状态与订阅？

### 自测题

1. 只改写累计文本的 state 更新表达式。
2. 给删除第一条消息的列表选择一个不会漂移的 key。
