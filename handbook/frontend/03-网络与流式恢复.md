# 第 3 章 网络与流式恢复

依赖：异步执行、运行时输入校验和任务状态机。应用协议需先说清，再选 EventSource、fetch 流或 WebSocket。

## fe.web.http —— 网络边界各自保证什么

### 结论

HTTP 状态、缓存、跨域策略和业务授权解决不同问题；浏览器允许读取响应不代表请求被业务授权。

### 案例

前端 `fetch` 返回后直接显示成功，忽略了 403 响应；另一个部署把用户任务快照交给共享 CDN 缓存，用户切换后仍看到前一人的结果。开发者试图用 `mode: 'no-cors'` 解决跨域，得到无法读取的 opaque 响应。

### 机制

| 边界 | 能说明什么 | 工程动作 |
|---|---|---|
| fetch resolve/reject | HTTP 错误通常仍 resolve；网络/取消等才常表现为 reject | 检查 `response.ok`、内容类型，再解析已知响应契约 |
| CORS | 浏览器是否允许脚本读取跨源响应 | 服务端明确 origin/credentials；`no-cors` 不授予读取能力 |
| 身份与 CSRF | cookie 是否携带不等于动作获授权 | 服务端校验身份和对象权限；cookie 鉴权写请求配置 CSRF 防护 |
| 缓存 | 新鲜度、共享范围和重新验证 | 区分私有响应与公共资源；含敏感任务数据可选择 `no-store` |
| 重试 | 请求结果可能未知 | GET 查询可按预算重试；有副作用的 POST 依服务端幂等契约 |

`no-cache` 允许存储但要求使用前重新验证；它不等于 `no-store`。对带凭据的跨源读取，通配 origin 不能代替明确允许来源。CORS 也不能拦住所有跨站发送，所以不能充当 CSRF 防线。token、消息正文与审批凭据不放 URL，避免进入历史与访问日志。[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)、[HTTP 缓存](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

### 误解靶子

“没有抛异常就是 2xx。”“后端开了 CORS，所以接口已经安全。”它们混淆了不同边界。

### 判据

收到合法 HTTP 响应但业务拒绝时，是否仍会进入成功状态？

### 自测题

1. 只为 fetch 返回 403 选择客户端下一步分支。
2. 给包含私人会话的快照选择一种不会被共享缓存复用的策略。

## fe.stream.recovery —— 重连的是事件进度

### 结论

恢复流式任务依靠任务身份、可重放游标与幂等事件应用；重新打开连接不等于恢复进度。

### 案例

客户端收到“你”“好”两个 delta 后断网，重连时服务端重放第二个 delta，页面显示“你好好”。后来把相同文字去重，用户真正重复说出的“好”又被丢掉。

### 机制

先分清三层边界：

```text
网络字节块 → UTF-8 增量解码 → SSE 完整帧 → JSON 校验 → 应用事件 → 状态投影
```

一块字节可只有半个汉字或半条 `data:`，也可含多帧。SSE 以空行结束帧，多行 data 要按规则合并；冒号注释不是业务事件。原生 EventSource 负责解析与自动重连，可带 Last-Event-ID；fetch 读流需自己处理 decoder、缓冲、帧解析与重连。原生 API 不提供任意自定义请求头/POST body，需结合部署鉴权方案选型。[SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)、[ReadableStream](https://developer.mozilla.org/en-US/docs/Web/API/Streams_API/Using_readable_streams)

本书工作台采用以下**应用契约**，不是 SSE 标准字段：

| 字段 | 约束 |
|---|---|
| `schema_version` | 当前示例接受 1；不支持版本进入升级/错误路径 |
| `run_id` | 每次任务不同；不能拿新任务接续旧任务 |
| `seq` | 任务内从 1 起连续递增，编号与事件内容不可复用或改写；只有完整事件应用后推进游标 |
| `type`、payload | text.delta / tool.updated / approval.required / run.completed 等可辨识事件 |

重连请求同一 run 在已应用 seq 之后的事件。`seq <= last_seq` 是重复，忽略；`seq > last_seq + 1` 是缺口，暂停应用并补历史或取快照；恰好下一条才能应用。游标与投影应一起保存，否则刷新后“游标超前、正文没保存”会漏字。多生产者、过滤流或多个 channel 若不保证连续序号，需重新定义可证明的水位协议，不能照搬这个条件。

服务端保留历史才能重放；游标过期时提供带 `last_seq` 的任务快照，再从该位置续流。流意外 EOF 保留未知连接状态；只有经过校验的任务终态事件/快照才能结束任务。终态后关闭连接，避免原生自动重连反复访问已完成任务。

| 情况 | 本书约定 |
|---|---|
| 网关/浏览器缓冲 | 检查代理缓冲与刷新，不把“服务端 write”当成“用户已见” |
| 心跳到达 | 只证明连接活着，不证明工具有进展 |
| 瞬时断网 | 有界退避重连；收到 401/403 转鉴权处理，避免无限重试 |
| 用户停止 | 先表达 cancel_requested，再等任务权威状态；本地关流不假装后端已停 |

原生 EventSource 的 error 回调不直接暴露 HTTP 状态码；上表的鉴权分支需要 fetch 传输或独立的会话/鉴权查询协助判断，不能在原生 onerror 中凭空读取401。应用自行重建 EventSource 时也要自行携带已应用游标；浏览器内部 Last-Event-ID 与应用落盘游标不是同一事务。

SSE 适合服务端到客户端事件推送；WebSocket 提供双向消息通道，但同样需要应用层身份、重放、顺序和授权。选择依据是交互方向与基础设施约束，不是“哪个更先进”。

### 误解靶子

“按内容去重。”“EventSource 自带 exactly-once。”“read() 返回一条完整 JSON。”这些保证都不存在于上述边界。

### 判据

把同一事件流任意分片、重复投递并断线重放，最终投影是否与完整处理一次相同？

### 自测题

1. `last_seq=8` 却收到 seq=10，只指定下一步恢复动作。
2. “好”在 seq=8 与 seq=9 各出现一次，只判断是否应保留两次。
3. 本地取消 fetch 后，只判断能否标记服务器任务为 cancelled。
