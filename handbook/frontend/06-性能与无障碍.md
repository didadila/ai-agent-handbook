# 第 6 章 性能与无障碍

依赖：布局、渲染路径、任务状态和生命周期。聊天越长、输出越快，越需要保证用户仍能输入、定位信息和停止任务。

## fe.perf.streaming —— 按用户交互预算处理增量

### 结论

控制每次渲染的工作量和保留数据的规模；降低 render 次数只是手段，交互能及时完成才是目标。

### 案例

每个 token 都把整段 Markdown 重新解析、对全部历史消息做高亮并滚到底部。输出越长，重复解析越多；用户滚上去看引用，又被拉回底部。把所有工作放进 rAF 之后，卡顿依然存在。

### 机制

| 成本来源 | 处理边界 | 需要检查的代价 |
|---|---|---|
| 高频小 delta | 缓冲后合并更新；任务结束时 flush 剩余内容 | 合并窗口增加可见延迟，不能丢最后一块 |
| 全文重复解析 | 分段提交、缓存已完成块；未闭合 Markdown 使用安全展示策略 | 不能把不完整标签交给不安全的 HTML 拼接 |
| 长历史 DOM | 窗口化列表，测量可变高度 | 焦点、文本选择、查找与滚动锚点需要补偿 |
| 重型纯计算 | 分批让出主线程或放 worker | worker 仍有复制/传输成本，不能直接操作 DOM |
| 消费慢于输入 | 有界缓冲；必要时暂停读取或用快照恢复 | 不能静默丢审批、错误和完成事件 |

先记录完整性能轨迹，再看输入等待、处理与呈现各占多少。INP 关注用户交互到下一次绘制的延迟；Agent 首字延迟、任务完成时间和浏览器输入延迟是不同指标，不能只看模型 tokens/s。阈值按目标设备、数据规模与产品要求设定，不把教学数字写成通用门限。[INP 优化](https://web.dev/articles/optimize-inp)、[渲染与布局成本](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)

自动滚动只在用户接近底部且未主动离开时跟随；展示“有新消息”入口让用户返回。性能优化不应偷换这条交互约定。

### 误解靶子

“加 memo 就够了。”“每秒字更多说明体验更好。”“删掉慢消费者的中间事件就行。”这些都没指定实际成本或事件语义。

### 判据

在目标设备和最长支持会话下，持续生成时一次输入或停止操作是否仍满足已声明的延迟预算？

### 自测题

1. 性能轨迹显示重活全在一次 Markdown 解析，只选择一个应先切分的计算边界。
2. 用户已向上滚动，只指定下一块 delta 到来时的滚动策略。

## fe.a11y.status —— 状态可感知，操作可到达

### 结论

关键动作要能用键盘完成，状态变化要能被辅助技术感知，同时保留用户的阅读位置与焦点。

### 案例

整个聊天区使用 `aria-live="assertive"`，每个 token 都触发播报，读屏用户无法听完自己的输入。弹出审批后焦点仍在背景输入框；关闭弹窗后又跳到页面顶部。

### 机制

语义控件与可见焦点是基础；模态审批需要清晰名称、合理初始焦点、受控焦点范围和关闭后返回触发位置。状态区报告“工具执行中”“需要审批”“已结束”等有意义的阶段，不把每个 token 都作为高优先级消息。通常使用合适的 status/live 区域，紧急错误才按需要打断。交互状态不只靠颜色表达，加载也要有文字或可访问名称。[W3C 状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)、[WAI 模态对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

长列表窗口化可能卸载当前焦点或让引用目标不存在，需要保留焦点项、定位后渲染目标并告知位置。动效考虑减少动态效果偏好；窄屏和放大下控件仍应可达。自动化可检查名称与焦点，但读屏实际播报顺序还需人工验证。

### 误解靶子

“ARIA 越多越好。”“能截图看到就算可访问。”“自动扫描通过就证明键盘和读屏全正常。”标记无法替代完整操作链。

### 判据

从输入任务到停止、审批、返回阅读位置，键盘与读屏用户能否独立完成？

### 自测题

1. 只指定关闭审批弹窗后焦点应回到哪里。
2. 为每 token 播报选择一个减少打断的状态更新粒度。
