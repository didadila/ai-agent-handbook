# 新建领域包模板

用户要考的领域在 `references/domains/` 下没有对应包时，用这个骨架起一个。

## 最小可用形态

一个领域包只需要 `map.md` 就能跑起来。`questions.md` 是可选的加速件——有它就省去现场设计追问链的成本，没它就按 `references/question-design.md` 的四步法现场出题。

所以新建领域包时**先把图谱写出来，不要卡在题库上**。写 30 条追问链是个大工程，写一个 40 行的依赖排序图谱是一次会话就能做完的事。

```
references/domains/<领域名>/
├── map.md          # 必需
└── questions.md    # 可选，覆盖高频点即可
```

领域名用小写加连字符（`java-backend`、`ai-agent`、`kubernetes`），因为它同时是状态文件的目录名（`~/Documents/learning/<领域名>/`）。

## map.md 骨架

```markdown
# 领域包：<领域名> — 知识图谱

覆盖 <一句话说明范围>。配套题库在同目录 `questions.md`（只覆盖高频点，其余按 `references/question-design.md` 现场出题）。

按依赖排序。**L1 是 L2 的前提，L2 是 L3 的前提。** 跳级出题会让用户只能背书。

每个知识点带稳定 ID，写状态文件时用这个 ID，不要用中文名（中文名可能被改写，ID 不会）。

「常见误解」一栏是出题时的靶子：如果用户的回答命中了这些，说明他停在了一个具体的错误模型上，值得针对性追问。

---

## 1. <模块名>

| ID | 层级 | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|---|
| `<前缀>.<子域>.<点>` | L1 | | | |

---

## 组题建议

**一次会话的合理配比**：到期复习 2-3 题 + 同一模块内相邻知识点 2-3 题 + 一个 L3 综合题（用设计评审人格问）。

**不要在一次会话里横跨 5 个模块。** 同一模块内连续追问才能形成知识链条，跳着问就只是刷题。

**首次定位的三题建议**：<一个 L1 的点>、<一个 L2 的点>、<一个 L3 的点>，并说明各自想测出什么。
```

## 写图谱时最容易出的四个问题

**「该考什么」写成了知识点的定义。** 这一栏是给出题用的，要写"问哪个角度能区分真懂和背书"，不是写这个概念是什么。对比一下：❌「B+ 树是一种多路平衡查找树」 ✅「为什么不用 B 树/红黑树/哈希；三层能存多少行；扇出和树高的关系」。

**「常见误解」写成了"不知道"。** 要写用户会说出口的**具体错误模型**（"认为 G1 取消了分代"），这样你在他开口三个字时就知道往哪追。写"不了解 G1"没有任何出题价值。

**层级只是标了个 L1/L2/L3，实际没有依赖关系。** 检验办法：随便挑一个 L2 的点，问自己"哪个 L1 的点是它的前提"。答不上来，说明分层是按难度感觉标的，不是按依赖标的——那组题时就没法避免跳级。

**ID 用了会变的名字。** ID 会被写进用户的错题本，改一次 ID 就等于把那条历史记录变成孤儿。所以 ID 里不要放版本号、产品名、框架名这类会过期的东西：用 `agent.ctx.compaction` 而不是 `langchain.memory.summary`。

## 知识在快速变化的领域

AI、大模型、Agent 这类领域，具体框架的 API 半年就换一轮，但结构性的问题（上下文预算怎么分、工具失败怎么处理、非确定性系统怎么做回归）多年不变。

**图谱只写结构层，不写当代实现细节。** 前者能用三年，后者写完就开始烂——更糟的是，烂掉的图谱会让你用过时的认知去判用户的档位，把 A 档答案判成 D 档。

出题前对某个机制的当前状态没把握，先 WebSearch 确认再问。
