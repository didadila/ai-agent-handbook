# 领域包：ai-agent — 知识图谱

跨领域应用：浏览器流式恢复、审批交互与输出渲染见[frontend 图谱](../frontend/map.md)，其状态与判档独立。本域仍考 Agent 决策与运行机制，不把 UI 实现当成本域新增点。

> 结构层核验：2026-10-30｜趋势证据：见同目录 `sources.md`｜维护：见 `maintenance.md`

覆盖Agent工程33个稳定点，题库逐点覆盖。题库是入口，变体按references/question-design.md设计；面经映射见interview-bank.md，判档仍以机制为准。

按依赖排序。**L1 是 L2 的前提，L2 是 L3 的前提。** 跳级出题会让用户只能背书——比如不理解模型为什么会幻觉，问 RAG 怎么降幻觉就只能得到「加了检索让它有依据」这句复述。

每个知识点带稳定 ID，写状态文件时用这个 ID，不要用中文名（中文名可能被改写，ID 不会）。

「常见误解」一栏是出题时的靶子：如果用户的回答命中了这些，说明他停在了一个具体的错误模型上，值得针对性追问。

## 这个图谱刻意只写结构层

Agent 领域的框架 API、模型能力、最佳实践半年一轮换，但下面这些问题多年不变：上下文预算怎么分配、工具失败怎么分类处理、非确定性系统怎么做回归、多 agent 拆分的通信代价。图谱只覆盖这一层，原因不是省事，而是**过时的图谱比没有图谱更糟**——它会让你用两年前的认知去判用户的档位，把对的答案判成错的。

所以出题时如果碰到某个机制的当前状态没把握（尤其是模型侧能力、协议细节），先 WebSearch 确认再问。这个领域教错东西的代价特别高，因为用户没有别的参照来纠正你。

## 0. Agent 适用边界与运行时（L1→L3）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.arch.workflow` | Workflow 还是 Agent | 预定义路径与动态决策的边界、何时不该 Agent 化、为什么应从简单方案起步 | 认为任务复杂就必须用 Agent，或 Agent 一定比 workflow 更先进 |
| `agent.runtime.durable` | 耐久执行 | checkpoint、暂停恢复、外部状态、幂等副作用、版本迁移与执行前复验分别解决什么 | 认为模型有长上下文、计划写得细，就等于任务能可靠地跑几小时 |
| `agent.protocol.interop` | 协议与业务语义 | MCP 类工具协议与 A2A 类 agent 协议各解决什么；schema、认证声明与业务授权的边界 | 认为接入开放协议就自动获得互操作、安全、幂等和正确恢复 |

依赖顺序：先判断是否真的需要动态决策，再讨论循环、规划、子 agent 和长期记忆。`agent.protocol.interop` 的具体版本属于趋势层，出题前核对 `sources.md`。

## 1. 模型能力与边界（L1，所有上层的前提）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.llm.generation` | 逐 token 生成 | 输出是逐 token 采样出来的、temperature/top-p 在改什么、为什么同一输入两次结果不同 | 认为模型"想好了再答"，因此期待它能自我修正已经输出的内容 |
| `agent.llm.context` | 上下文窗口 | 窗口是什么、token 化的影响、长上下文里中段信息为什么容易被忽略 | 认为只要没超窗口，塞多少信息都等效 |
| `agent.llm.hallucination` | 幻觉的来源 | 为什么是生成机制的固有结果而不是 bug、哪些任务上必然发生、检索为什么只能缓解不能消除 | 认为幻觉是训练数据不够导致的、能靠提示词彻底禁止 |
| `agent.llm.stateless` | 无状态与会话 | 模型每次调用都不记得上一次，"记忆"是外部拼上下文实现的 | 认为模型自己在维护会话状态 |

## 2. 上下文工程（L2）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.ctx.budget` | 上下文预算与组装 | 窗口是有限资源，系统提示/工具定义/历史/检索结果如何争抢；为什么长期任务要按当前决策每轮重建最小充分上下文 | 认为"能塞就塞"，或把上下文窗口当作任务状态数据库 |
| `agent.ctx.compaction` | 压缩与摘要 | 什么时候压、压掉什么会导致行为退化、为什么压缩后仍要保留可追溯原始事件 | 认为摘要是无损的，压完不会影响决策质量或审计能力 |
| `agent.ctx.memory` | 记忆生命周期 | 选择性写入、召回、拼接、遵守、失效/覆盖、作用域、冲突合并与删除传播；记忆和任务状态的区别 | 把"存下来"等同于"记住了"，或认为新记忆总能自动覆盖旧事实 |
| `agent.ctx.pollution` | 上下文污染 | 失败记录、错误结论、重复动作留在上下文里会怎么影响后续决策 | 认为多给信息总是更好，没意识到错误信息会被当成事实继承 |
| `agent.ctx.injection` | 提示注入 | 不可信内容（网页、文件、工具返回）进上下文后的风险、为什么"让模型别听"不是防御 | 认为在系统提示里写"忽略指令"就能防住 |

## 3. 工具调用（L2）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.tool.protocol` | 调用机制 | 工具定义如何进入模型、选择和参数为何仍是生成结果；schema 能校验形状但为何不能保证业务语义 | 认为结构化调用是框架的确定性规则匹配，或有 schema 就不会越权/编造 |
| `agent.tool.design` | 工具设计 | 粒度怎么定、必填参数集与恢复动作何时要求拆分、列表/详情返回契约、工具竞争和固定上下文代价 | 认为 description 能修复重叠语义，或工具越多越强 |
| `agent.tool.errors` | 失败与恢复契约 | 协议错误、参数错误、业务拒绝、限流、超时未知状态如何分类；错误如何携带机器可执行的恢复信息 | 一律重试固定次数，或把原始栈直接丢回模型让它猜恢复动作 |
| `agent.tool.sideeffect` | 副作用与幂等 | 哪些工具不可重试、超时后状态未知怎么处理、破坏性动作的确认边界 | 认为超时就是没执行 |

## 4. 检索（L2）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.rag.chunking` | 切分 | chunk 大小的两头代价、跨 chunk 的答案怎么办、结构化文档为什么不能按字数切 | 认为存在一个通用最优 chunk 大小 |
| `agent.rag.retrieval` | 检索策略 | 向量/关键词/混合各自漏什么、rerank 解决的是召回还是排序问题、top-k 怎么定 | 认为向量检索天然优于关键词，能覆盖所有查询类型 |
| `agent.rag.quality` | 检索质量的影响 | 检索回错内容时模型会怎么做、召回率高但精度低的后果、矛盾来源怎么处理 | 只盯召回率，认为多召回没坏处 |
| `agent.rag.grounding` | 归因与溯源 | 怎么让答案可追到出处、引用对象存在与证据蕴含断言的区别、原子断言如何逐条绑定证据 | 认为模型输出的引用一定支持它前面的全部断言 |
| `agent.rag.evaluation` | RAG 分层评测 | 召回、排序、上下文噪声、答案正确性、忠实性、引用完整性/蕴含如何分层定位 | 用一个端到端正确率评价整条链，结果错了却不知道修哪层 |

## 5. Agent 循环与控制（L2→L3）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.loop.basic` | 推理-行动循环 | 为什么需要多轮而不是一次生成、每轮上下文如何累积、终止条件怎么定 | 认为循环次数上限是唯一的终止手段 |
| `agent.loop.planning` | 规划与重规划 | 计划是一组基于有限信息的假设；新工具结果出现后何时重验剩余步骤前提 | 认为顺序正确、每步成功就等于计划仍然正确，或把计划写细就能减少失败 |
| `agent.loop.subagent` | 子 agent 与上下文隔离 | 任务依赖图是否可并行、parent 能否独立复验完整性、交接信息损失与错误放大 | 认为拆得越多越可靠，或只按文件/数量切分而不看依赖边界 |
| `agent.loop.humanloop` | 人在环 | 确认点该插在哪、按什么判据插（可逆性、影响范围）、过度确认的代价 | 按"重要性"直觉插确认，而不是按可逆性 |

## 6. 评估（L3）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.eval.design` | 评估设计 | baseline、未被调优过的样本、多次运行；为什么要同时看终态、轨迹、业务代价与环境差异 | 跑几个 case 看最终输出好不好就当评估过了 |
| `agent.eval.assertion` | 断言与硬门 | 结果性质、轨迹不变量、副作用/权限/成本门限如何分层；哪些维度不能加权抵消 | 认为断言越多越严格，或任务成功能抵消越权和破坏性动作 |
| `agent.eval.judge` | 模型做裁判 | 适用边界、位置/长度偏好、如何用保留的人类标注集校准和监测漂移 | 认为换个更强的模型做裁判就客观了，或扩大样本能消除系统偏差 |
| `agent.eval.regression` | 随机系统回归 | 逐 case 配对、flaky 噪声带、稳定 pass→fail；pass@k 与 pass^k 分别回答什么 | 只看平均总分，或把“至少一次能成功”当成“每次都可靠” |

## 7. 失败模式与工程化（L3）

| ID | 名称 | 该考什么 | 常见误解 |
|---|---|---|---|
| `agent.fail.modes` | 典型失败模式 | 原地打转、过早收敛、工具误用、自我确认；每种的可观测信号 | 把所有失败都归因为"模型不行" |
| `agent.fail.observability` | 轨迹可观测性 | task root span 如何串起模型/检索/工具/交接；状态快照与重放条件；为什么内容载荷默认不记录 | 只记入参和最终结果，或为了复现把 prompt、密钥和用户数据全量写进日志 |
| `agent.cost.latency` | 任务级成本与尾延迟 | cost per successful task、端到端 p50/p95/p99；缓存、路由、并行、批处理的收益条件和反向成本 | 只看单次调用 token/均值，或认为换小模型、开并行一定降本提速 |
| `agent.safety.boundary` | 权限、身份与破坏半径 | 可逆性×影响范围、调用者身份注入、短期最小权限凭证、资产集合×出口集合、跨主体审计路径 | 用模型生成鉴权字段，或用一次授权覆盖后续所有同类动作 |

## 2026 趋势层（出题前核验 `sources.md`）

| 趋势 | 可考的稳定机制 | 不可直接当成永久结论 |
|---|---|---|
| MCP / A2A 协议化 | 协议只定义交互和能力表达，业务授权、幂等与恢复仍由实现负责 | 当前字段、版本号、生态兼容程度 |
| 多 Agent 扩展 | 先看任务依赖图、并行性、交接与 parent 可复验能力 | 固定 agent 数、统一提速率或成本倍率 |
| 长期记忆基准 | 过期、冲突、作用域与删除传播必须进入生命周期 | 某一记忆框架或“记忆 OS”天然更优 |
| GenAI 可观测性标准 | 一条任务 trace 应覆盖模型、工具、交接和业务结果 | 尚在演进的 span/attribute 名称 |
| Context / prompt caching | 缓存复用计算，不等于记忆；收益依赖稳定前缀、长度、TTL 和复用率 | 厂商当前价格、固定降本比例和阈值 |

## 组题建议

**一次会话的合理配比**：到期复习 2-3 题 + 同一模块内相邻知识点 2-3 题 + 一个 L3 综合题（用设计评审人格问）。

**不要在一次会话里横跨 5 个模块。** 同一模块内连续追问才能形成知识链条——问完 `agent.ctx.budget` 紧接着问 `agent.ctx.compaction`，用户能自己发现"压缩是预算不够时的必然手段，而不是一个可选优化"这个结构。跳着问就只是刷题。

**这个领域尤其要守住依赖顺序。** 不理解 `agent.llm.generation`（输出是逐 token 采样的）就问 `agent.llm.hallucination`，用户只能答"训练数据不够"；不理解 `agent.ctx.budget` 就问 `agent.rag.chunking`，chunk 大小的取舍在他看来就是个调参问题。这个领域的二手结论特别多，容易问出一片 C 档。

**首次定位的三题建议**：
- `agent.llm.stateless`（L1）— 几乎人人"知道"要拼历史，正好用来测他是否理解记忆是外部拼装的
- `agent.tool.protocol`（L2）— 能不能说出工具定义是 prompt 的一部分，一句话分出 C 档和 B 档
- `agent.eval.design`（L3）— 有没有 baseline 意识。这题答得出的人，工程素养基本可靠
