## 语言前提

### `go.lang.value` slice 的 cap 与 nil

**首题**：

```go
all := []Item{{1, "a"}, {2, "b"}, {3, "c"}}
part := all[:2]
part[0].Name = "changed"
part = append(part, Item{4, "d"})
```

`all[0].Name` 和 `all[2]` 分别是什么？两个动作要分开解释。

**追问链**：
- L1：`part` 的 len 和 cap 各是多少？cap 为什么不是 2？
- L2：如果 `take` 返回 `items[:n:n]`，append 的结果会变吗？为什么？
- L3：`var m map[string]int; m["a"]=1` 和 `var s []int; s=append(s,1)`，一个 panic 一个正常，机制差别在哪？

**A 档要点**：① 下标写改的是底层数组，一定影响 `all` ② append 是否复用取决于 len<cap；`all[:2]` 的 cap 延伸到原数组末尾 ③ `[:n:n]` 把 cap 夹成 n，append 新分配 ④ nil map 没有哈希表，写 panic；append 是函数，cap 不够会自己分配 ⑤ append 返回新头，必须赋回

**错误答法识别**：
- 「会，因为指向同一内容」→ 结论对、机制错。追问「cap 刚好等于 len 时呢」
- 「不会，append 总是新数组」→ 追问「那为什么调用方的数据被改了」
- 「nil 就是空，读写都没事」→ 直接给 nil map 写入的例子

### `go.lang.interface` typed nil

**首题**：

```go
func do() error {
    var e *MyErr = nil
    return e
}
if err := do(); err != nil { ... }
```

这个 `if` 会进吗？为什么？

**追问链**：
- L1：接口值在内存里由哪两部分组成？
- L2：类型是 `*MyErr`、值是 nil，为什么整个接口不等于 nil？
- L3：怎么避免？构造函数返回、显式 `return nil`、还是调用方用 `errors.Is`？

**A 档要点**：① 接口是 `(动态类型, 动态值)` ② 只有两者都为 nil，接口才等于 nil ③ typed nil 赋给接口后类型非空，所以 `err != nil` ④ 修法是返回真正的 nil，或在具体类型上判空

**错误答法识别**：
- 「nil 指针就是 nil」→ 追问「为什么 `err != nil` 为真」
- 「用 `err == nil` 判断就够了」→ 追问 typed nil 场景

## 并发与生命周期

### `go.conc.goroutine` 没有退出条件的 goroutine

**首题**：线上内存从 300MB 涨到 1.9GB，pprof 显示 4 万个 goroutine 卡在同一个下游调用上。它们为什么还占着内存？如果下游永远不恢复会怎样？

**追问链**：
- L1：goroutine 阻塞在 IO 上时，OS 线程被释放了吗？栈还在吗？
- L2：这些 goroutine 缺了什么，才会一直不退出？
- L3：入口 QPS 是 500，每个请求 `go` 一个任务，下游并发是多少？上限应该由谁定？

**A 档要点**：① 阻塞的 goroutine 不占 OS 线程，但栈和调度信息还在 ② 缺超时/取消，或 channel 永远等不到 ③ 每个请求起一个 goroutine = 把入口 QPS 放大成下游并发 ④ 必须有界：worker 数/信号量/超时/队列长度

**错误答法识别**：
- 「加机器」→ 追问「下游被打挂之后，加机器有用吗」
- 「goroutine 很轻，几万个没事」→ 追问「轻是相对线程，那内存从哪来」

### `go.conc.context` 取消没有传下去

**首题**：handler 里设了 2 秒超时，但下游 DB 查询用了 `context.Background()`。请求超时返回 504 之后，DB 查询会停吗？为什么？

**追问链**：
- L1：`WithTimeout` 返回的 ctx 和 `Background()` 是什么关系？
- L2：取消是怎么传播到下游的？靠什么机制？
- L3：哪些调用必须收 ctx？只传一半会怎样？

**A 档要点**：① 取消是树，子 ctx 从父 ctx 派生才传播 ② `Background()` 是树根，永远不会被取消 ③ DB/HTTP/RPC 都要显式传 ctx ④ handler 返回不代表下游停止，连接和查询可能还在跑

**错误答法识别**：
- 「超时了就会自动断」→ 追问「谁去断？下游怎么知道」
- 「每个函数里自己 `WithTimeout`」→ 追问「和上游的预算怎么对齐」

## 服务边界

### `go.svc.idempotency` 超时后的重试

**首题**：调用扣款接口超时，客户端自动重试了一次，用户被扣了两次。超时到底说明了什么？重试前应该先做什么？

**追问链**：
- L1：超时是「请求没到」「请求到了没执行」还是「执行了没返回」？能区分吗？
- L2：幂等键应该由谁生成？存在哪？唯一约束加在哪？
- L3：如果两个相同请求同时到达，只靠「先查有没有」够吗？

**A 档要点**：① 超时只说明没收到响应，不说明对方没执行 ② 幂等键 + 唯一索引 + 结果复用 ③ 查询和写入之间有并发窗口，必须靠唯一约束兜底 ④ 不可逆动作重试前先查状态，或让对端去重

**错误答法识别**：
- 「重试是安全的，接口应该幂等」→ 追问「接口现在幂等吗？谁保证」
- 「先 SELECT 再 INSERT」→ 追问「两个请求同时 SELECT 都为空呢」

### `go.svc.timeout` 超时预算

**首题**：网关 3s，服务 2.5s，下游 1s，DB 没设。这个链路最坏要多久？哪一层会成为短板？

**追问链**：
- L1：`http.Server` 不设 `ReadTimeout/WriteTimeout` 时是多少？
- L2：`http.Client` 零值的 `Timeout` 是多少？为什么默认无超时很危险？
- L3：每层超时应该怎么分配？为什么不能四层都设 3s？

**A 档要点**：① 零值 = 无限，不是默认值 ② 超时要逐层递减并留处理余量 ③ 任何一层没设，上层设了也会被拖死 ④ 网关 504 只是结果，不是超时机制

**错误答法识别**：
- 「默认应该有超时」→ 直接给零值行为
- 「每层都设 3s 就行」→ 追问「下游 3s 没返回，上游还有时间返回吗」

## 数据与一致性

### `go.data.tx` 事务里的外部调用

**首题**：一个事务里先写订单表，再调 LLM 生成摘要，最后发 MQ。LLM 超时导致事务回滚，订单没写成功，但 LLM 已经扣了钱、MQ 也可能发出去了。问题出在哪？

**追问链**：
- L1：事务能保证跨系统的原子性吗？能回滚外部副作用吗？
- L2：事务里做网络调用还有哪些代价？（持锁、连接占用、WAL）
- L3：应该怎么拆？先写本地、再异步，还是 Outbox？

**A 档要点**：① 事务只保证同库同事务内的原子 ② 外部调用不受回滚控制 ③ 长事务持锁、撑 WAL、占连接 ④ 拆成「本地事务 + Outbox + 异步投递」

**错误答法识别**：
- 「放在事务里就能一起成功或失败」→ 追问「LLM 的钱怎么回滚」
- 「加重试」→ 追问「重试的是事务还是外部调用」

### `go.data.consistency` 消息丢了没人知道

**首题**：订单写库成功，发 MQ 时网络抖动失败，代码只打了一行日志。下游没收到消息，库存没扣。这个不一致会自己恢复吗？谁会发现？

**追问链**：
- L1：MQ 的投递语义是至少一次、至多一次还是恰好一次？
- L2：Outbox 解决的是哪两个失败场景？为什么必须和业务写同库同事务？
- L3：消费方重复收到消息会怎样？幂等键放哪？对账多久跑一次？

**A 档要点**：① 常见 MQ 是至少一次 ② Outbox 把「写业务」和「写待发消息」放同一事务 ③ relay 投递、消费幂等 ④ 对账兜底，回答「谁发现、多久发现、怎么修」

**错误答法识别**：
- 「消息队列保证不丢」→ 追问「生产者发失败呢」
- 「失败了重发就行」→ 追问「进程在重发前挂了怎么办」

## 可观测性

### `go.obs.trace` 5% 的慢请求

**首题**：P95 正常，但有 5% 的请求超过 3 秒。日志里只有「请求完成」，你怎么定位慢在哪一段？

**追问链**：
- L1：日志、指标、trace 各自回答什么问题？能互相替代吗？
- L2：一次请求要打哪几条日志？字段固定在哪几个？
- L3：Agent 场景要多记哪一层？为什么普通 HTTP trace 不够？

**A 档要点**：① 日志回答「发生了什么」，指标回答「整体怎样」，trace 回答「慢在哪段」 ② 入口/出口/依赖/状态变更各一条，带 request_id ③ 均值会掩盖长尾，看 P95/P99 ④ Agent 要加 step / LLM 调用（模型、token、首 token 延迟）/ 工具调用

**错误答法识别**：
- 「多加日志」→ 追问「加在哪、打几条、怎么串起来」
- 「看监控大盘」→ 追问「大盘能告诉你卡在 DB 还是卡在 LLM 吗」

## Agent 平台后端

### `go.agent.gateway` 首 token 之后上游失败

**首题**：流式接口已经向客户端吐出 200 个 token，此时上游供应商返回 500。能不能悄悄换一家供应商从头重放？为什么？

**追问链**：
- L1：首 token 之前和之后，失败处理有什么本质区别？
- L2：不能重放的话，应该给客户端发什么？前端怎么区分「正常结束」和「中断」？
- L3：假设供应商把 usage 放在最后一块（OpenAI 要开 `include_usage` 才会给），客户端提前断开时怎么计费？
- L4：如果换一家供应商，usage 的位置变了（Anthropic 拆在 `message_start`/`message_delta`，Gemini 每块给累计值），网关该怎么统一？

**A 档要点**：① 首 token 是不可逆边界，之后只能中断并告知 ② 重放会让用户看到重复内容 ③ 用 error 事件结束流，并 flush ④ 计费在服务端，usage 缺失时估算 + 对账，不信客户端上报

**错误答法识别**：
- 「换一家重试，用户无感」→ 追问「已经吐出去的内容怎么办」
- 「客户端会重连」→ 追问「重连后从第几个 token 开始？上下文谁保存」

### `go.agent.runtime` kill -9 之后

**首题**：一个长任务正在执行第 3 步（已经调用了外部工具并产生副作用），进程被 kill -9。重启后这个任务应该怎么处理？

**追问链**：
- L1：任务状态、当前步骤、副作用记录分别存在哪？
- L2：怎么判断第 3 步「做没做」？工具本身不幂等怎么办？
- L3：worker 失联后谁接管？租约多长？接管后会不会重复执行？

**A 档要点**：① 状态机落库（agent_tasks/agent_steps） ② 每步记录开始/完成与幂等键 ③ 租约 + 心跳，过期由其他 worker 接管 ④ checkpoint/resume，而不是从头再来 ⑤ 审批是持久化状态，不是弹窗

**错误答法识别**：
- 「重启后重新跑一遍」→ 追问「已经扣的钱、已经发的消息怎么办」
- 「内存里记着进度」→ 追问「进程死了内存还在吗」

### `go.conc.race` 机制与边界
