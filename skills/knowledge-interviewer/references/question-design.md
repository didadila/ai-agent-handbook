# 自造题模板

题库覆盖不到的知识点——甚至整个没有领域包的领域——都靠这个方法现场出题。它给的是**结构**，不是题目。

掌握了这个模板，一个领域包其实只需要 `map.md`（该考什么）就能跑起来，`questions.md` 只是把高频点的追问链预制好、省一点现场设计的成本。所以新增领域时别被"要写几十条题"卡住，先写图谱。

## 四步法

**第一步：找到这个知识点的"设计决策"。**
每个技术机制都是在某个约束下做的权衡。找到那个权衡，追问链就自然有了三层。比如 ThreadLocal 的设计决策是"把 map 挂在 Thread 上而不是挂在 ThreadLocal 上"——一旦抓住这个，`Entry` 为什么是弱引用、为什么会内存泄漏、为什么 key 被回收而 value 不会，全都是这个决策的推论。

同样地，上下文压缩的设计决策是"用信息损失换窗口空间"——抓住这个，什么该压什么不能压、压完为什么会出现"忘了自己已经做过某步"、为什么要保留最近几轮原文，全都是推论。

如果找不到设计决策，说明你对这个点的理解还停留在"是什么"，这时不要硬出题——先自己想清楚，或者对快变化的领域先 WebSearch 确认。用一个自己都没想透的点去追问，会把用户带到错的地方。

**第二步：按这个顺序设计四个问题。**

| 层 | 问什么 | 目的 |
|---|---|---|
| L0 首题 | 这是什么 / 有什么用 | 建立话题，几乎所有人都能答，不用来区分水平 |
| L1 | 怎么做到的（机制） | 区分 C 档和 B 档——背过的人到这里就卡住 |
| L2 | 为什么这样设计 / 不这样会怎样（决策） | 区分 B 档和 A 档 |
| L3 | 代价是什么 / 什么场景下它是错的（边界） | 确认 A 档，也是最有教学价值的一问 |

**第三步：写下 A 档答案要点**，就三到四条，只写"必须提到才算真懂"的点。写太细会导致你按稿子核对，用户换个说法讲对了你也判错。

**第四步：预判两个常见错误答法**，并写下它们的**识别特征**（用户会说出的具体句子），而不是"答错了"这种描述。识别特征让你在用户说到第三个字时就知道该往哪追。

## 范例一（`java-backend`，题库里没有的点：为什么 Tomcat 要破坏双亲委派）

```
设计决策：双亲委派保证同一个类只被加载一次，但 Tomcat 需要同一个类在不同 webapp 里是不同的类。

L0: 双亲委派是什么？
L1: Tomcat 的 WebappClassLoader 怎么破坏它的？（→ 重写 loadClass，先自己找）
L2: 为什么必须破坏？不破坏会出什么问题？（→ 两个 webapp 用不同版本的同名类会冲突）
L3: 那 Tomcat 怎么保证 JDK 的核心类不被 webapp 覆盖？（→ 仍然对 java.* 走委派）

A 档要点：① 重写 loadClass 而非 findClass ② 目的是 webapp 间类隔离
        ③ 仍保留对 JDK 核心包的委派 ④ 知道这导致每个 webapp 有独立的静态变量

错误答法识别：
- "为了热部署" → 这是结果不是机制，追问"热部署具体依赖它哪一点"
- "重写了 findClass" → 混淆了两个方法，直接指出并问"findClass 和 loadClass 谁控制委派顺序"
```

## 范例二（`ai-agent`，题库里没有的点：为什么要给 agent 做工具调用的重试上限）

```
设计决策：模型的每一步都是概率性的，失败可能是暂时的（网络）也可能是系统性的（参数就是错的）。
无上限重试会让系统性错误变成无限循环，有上限则可能放弃一个本来会成功的调用。

L0: agent 调工具失败了应该怎么办？
L1: 你怎么区分"重试一次就能好"和"再试一百次也是这个结果"？（→ 机制：靠错误类型还是靠错误文本）
L2: 为什么不能简单地"失败就重试直到成功"？（→ 决策：系统性错误会打转，
    而且每轮都在往上下文里堆失败记录，越堆模型越倾向于重复同样的动作）
L3: 上限设成 3 次，什么场景下这个上限会伤害用户？（→ 边界：长耗时幂等操作、
    限流类错误其实该退避而不是放弃）

A 档要点：① 区分可重试错误和不可重试错误，而不是一律重试
        ② 失败记录本身会污染上下文，让模型陷入同一个错误动作
        ③ 重试要带退避，限流和超时的正确处理不同
        ④ 上限之外还需要一条"换方法"的路径，而不只是放弃

错误答法识别：
- "加个 try catch 重试三次" → 只有招式没有判据。追问"这三次里如果错误信息一模一样，
  第三次和第一次有什么区别？"
- "让模型自己决定要不要重试" → 追问"模型看到的上下文里有三条一样的失败记录，
  它下一步最可能做什么？"
```

## 整个领域没有包的时候

先花一轮做范围确认，不要直接出题：

1. **问用户这个领域他想搞懂哪一块**，以及他现在能做到什么、卡在哪。这一轮的目的是拿到出题范围，不是评分。
2. **当场列一个 5-8 个知识点的简版图谱**，按依赖排序，给用户看一眼确认方向对不对。跳过这步，你会出一堆他不关心的题。
3. 对**知识在快速变化的领域**，出题前用 WebSearch 确认关键机制的当前状态。宁可慢一轮，也不要用两年前的认知去判用户的档位——那会把 A 档答案判成 D 档。
4. 会话结束时按 `domains/_template.md` 把这个简版图谱落成一个新领域包的 `map.md`，下次就不用重来。

## 一个反复出现的失败模式

自造题最容易出的问题是**L1 和 L2 实际上是同一个问题的两种问法**。比如 L1 问"怎么做到的"、L2 问"原理是什么"——用户答完 L1 就没什么可说的了，追问链塌成两层，也就丧失了区分 B 档和 A 档的能力。

检验办法：L2 必须能被"如果不这样设计会发生什么"重写。如果重写不了，说明你的 L2 还停在机制层，得再往上找那个权衡。
